# 技术笔记

昇腾算子开发与 Kimi K3 部署过程中的技术内容汇总，分三部分：项目总览、问题与解决方案、部署优化体系与验证机制。

## 一、项目总览

### 算子与状态

| 算子 | 说明 | 状态 |
|---|---|---|
| SituAndMul（SiTU-GLU） | 自研 AscendC kernel | ✅ 已开发 + 对拍验证（d=11008 时 max_rel ≈ 7.5e-3） |
| AttnRes（残差栈） | 自研 AscendC kernel | ✅ 已开发 + 对拍验证（H=4096 时 max_rel ≈ 7.7e-3） |

结论：华为真正缺的算子只有 SiTU-GLU、AttnRes 两个，均已自研并验证通过。

### 验证方法论（无权重版）

1. 从 config 拿 shape/dtype
2. 固定 seed 生成随机输入
3. 参考实现跑出 golden 输出
4. 待开发算子跑候选输出
5. 对比：shape/dtype/layout 一致 + 数值误差在容差内（fp32→bf16 用 rtol=atol=1e-2）

## 二、问题与解决方案

### 2.1 部署需要多少卡、多少节点？

| 口径 | 答案 |
|---|---|
| 最小可行 | 64 卡 = 4 节点 Atlas 800 A3（DP4 / TP16 / EP64） |
| 生产（PD 分离） | 16 节点（8P+8D），每侧 DP8 / TP16 / PP1 |
| A3 + 1M 上下文 | ≥8 节点（DP8） |
| A2 混合部署 | 8 节点 × 8 卡（DP8 / TP8 / EP64，仅 256K，须 `--language-model-only`） |

> "千卡集群"是月活上亿的 Kimi 官方 MaaS 规模，与本地化部署不是一回事。官方验证配置照抄，不自己发明拓扑。

### 2.2 为什么是 64 卡？（可复算的显存账）

```
权重显存 = 2.8T 参数 × 每参数字节数
  ├─ MXFP4 常驻（0.5 B/参数） → 约 1.4~1.5 TB
  ├─ 反量化常驻 W8A8（1 B/参数） → 约 2.8 TB
  └─ FP16/BF16（2 B/参数） → 约 5.6 TB（不经济）
```

| 精度路径 | 纯权重卡数 | 含 KV/buffer（占用率 55~60%） | 结论 |
|---|---|---|---|
| MXFP4 常驻（推荐） | ~23 | ~40 | 工程取整 64 卡 |
| 反量化 W8A8 常驻 | ~44 | ~76 | 卡数近乎翻倍，不推荐 |

算力账（不是瓶颈）：

```
每 token FLOPs ≈ 2 × 104B 激活 = 约 208 GFLOP
1000 tokens/s → 约 208 TFLOPS → 按 30% MFU ≈ 700 TFLOPS ⇒ 仅约 1~2 卡等效算力
```

⇒ K3 是典型 memory-bound 部署：算力要 1~2 卡，显存要 40+ 卡，不能按算力估卡。

### 2.3 最大的坑：MXFP4 在 A3 不是硬件原生的

昇腾 A2 / A3（含 910C）硬件原生仅支持 INT8、FP8；MXFP4 原生支持属于 A5（950）/ Atlas 350。而 K3 原生权重是 MXFP4（group_size=32）。

A3 上必须走软件反量化：盘上保持 MXFP4，算时反量化成 W8A8/W4A8。两条路：

| 路径 | 做法 | 风险 |
|---|---|---|
| A. CANN 社区 recipe（推荐） | `cann-recipes-infer` 的 AscendC MXFP4→W8A8 融合算子；`KT_MXFP4_DEPOOL=1` 按需搬专家权重 | 需自行用 `bisheng` 编译 `libmxfp4fused.so` |
| B. msModelSlim 离线转换 | MXFP4 → W4A8 | 常驻 W8A8 权重时卡数从 ~40 涨到 ~76 |

⚠️ 另外：MindIE 不适配 K3（多机仅支持 TP、模型列表不含 K3），必须走 vLLM-Ascend / SGLang。

### 2.4 单卡能验证什么

参数账：

```
单专家参数量 = 3 × 3072 × 3584 ≈ 33 M
单 MoE 层 = 33M × 896 ≈ 29.6 B
92 个 MoE 层 ≈ 2.72 T（与总参 2.8T 自洽）

单层显存：MXFP4 ≈ 14.8 GB | BF16 ≈ 59.2 GB
```

⇒ "逐层加载仍溢出"发生在 BF16 载入单层（59.2GB）再转换那条路，不是 MXFP4 原样读取路径。

| 单卡能做 ✅ | 单卡不能做 ❌ |
|---|---|
| MXFP4 单层反量化 + 精度对拍（约 15GB） | 重新量化 / 校准（BF16 单层 59.2GB） |
| K3 特有算子正确性（SiTU-GLU、AttnRes、KDA） | HCCL 通信微基准（需 ≥2 卡） |
| 单专家精度（33M 参数） | MFU / TTFT / TPOT / EP64 均衡 / 1M Prefill 时延 |

### 2.5 「比华为提升多少」的正确口径

华为没有 SiTU-GLU / AttnRes（GLU 家族只有 SwiGlu/GeGlu/Glu，无 SiTU 变体），所以"相对华为提升"对这两个算子是假命题。正确对照是：

- 对照等价 torch 组合：加速比 4.45x~7.68x、带宽达标率 81.5%
- 能与华为直测的只有 KDA（精度差 4.4e-3）
- 同族 SwiGLU 只能比带宽达标率（数学不同，不能比谁准）

必带限定：省的是 HBM 往返不是时间（换时间要除带宽），且只对 prefill 放大（decode 占 0.065%）。

### 2.6 RDMA 实验不需要 NPU

RDMA 是网卡的事，跑在主机侧。昇腾机器就是一台 Linux，`rdma-core` / `perftest` 完全跑得起来。

环境探测：

```bash
ibv_devices
ibv_devinfo | grep -E "hca_id|link_layer|state|rate"
lspci -nn | grep -i -E "mellanox|infiniband|ethernet|huawei"
lsmod | grep -E "mlx|hns|hinic|rdma_rxe|ib_core"
rdma link show
```

| 结果 | 路径 |
|---|---|
| 有 `mlx5_0` / `hns_0` | 硬件 RDMA，直接 perftest |
| 只有普通以太网卡 | SoftRoCE（`rxe`） |
| 连 `ibv_devices` 都没有 | 装 `rdma-core`，或手写最小 ibverbs 程序 |

无硬件时的 SoftRoCE：

```bash
sudo modprobe rdma_rxe
sudo rdma link add rxe0 type rxe netdev eth0
ibv_devices
```

⚠️ SoftRoCE 性能数字无意义（走软件栈），但编程模型验证完整有效。

昇腾专属 `hccn_tool`：

```bash
hccn_tool -i 0 -link -g
hccn_tool -i 0 -net_health -g
hccn_tool -i 0 -ip -g
hccn_tool -i 0 -ping -g address <目标IP>
cat /etc/hccn.conf
```

RDMA ↔ HIXL ↔ ibverbs 对照（HIXL 是 CANN 开源的昇腾单边通信组件，也是 Mooncake 在昇腾上的传输底座）：

| RDMA 概念 | 通用 ibverbs | HIXL（昇腾） |
|---|---|---|
| 内存注册（pin） | `ibv_reg_mr` | `RegisterMem()` |
| 建连 | QP 状态机 INIT→RTR→RTS | `Connect()` |
| 单边传输 | `ibv_post_send` | `TransferSync()` |
| 释放内存 | `ibv_dereg_mr` | `DeregisterMem()` |

### 2.7 PD 分离集群

```
请求 → Proxy（调度）
        ├─ Prefill 节点：算完 prompt，产出 KV cache
        │      ↓  ★ KV cache 通过 RDMA 单边传输到 Decode 节点 ★
        └─ Decode 节点：拿到 KV，做自回归生成
```

PD 分离的本质是把 KV cache 从一台机器搬到另一台，这次搬运就是 RDMA 单边传输。

为什么要分离：Prefill 计算密集、Decode 访存密集，混在一起互相拖累；分离后 P/D 可各自用不同并行策略和独立扩缩容，直接收益是稳定 TPOT、优化 TTFT。

vLLM 和 SGLang 通常不用改代码，PD 分离是两个框架的内建特性，靠启动参数 + proxy 实现。

vLLM-Ascend：

```bash
# Prefill 节点
vllm serve $MODEL --port 8004 --tensor-parallel-size 8 --enable-expert-parallel \
  --kv-transfer-config '{"kv_connector":"MooncakeLayerwiseConnector",
    "kv_role":"kv_producer","kv_port":"30000","engine_id":"0",
    "kv_connector_module_path":"vllm_ascend.distributed.mooncake_layerwise_connector",
    "kv_connector_extra_config":{"prefill":{"dp_size":2,"tp_size":8},
                                 "decode":{"dp_size":32,"tp_size":1}}}'

# Decode 节点：kv_role 改 kv_consumer、kv_port 改 30200、engine_id 改 2
```

SGLang：

```bash
# Prefill
python -m sglang.launch_server --model $MODEL --port 30000 \
  --disaggregation-mode prefill --disaggregation-transfer-backend ascend \
  --disaggregation-bootstrap-port 8998
export ASCEND_MF_STORE_URL="tcp://<PREFILL_HOST_IP>:24669"
```

connector 选型：

| Connector | 传输方式 | 特点 |
|---|---|---|
| `MooncakeConnectorV1` | D 节点 pull KV（整块） | 简单，无重叠 |
| `MooncakeLayerwiseConnector` | P 节点逐层 push | 计算与传输重叠 ← 优先 |
| `MooncakeConnectorStoreV1` | `kv_role: kv_both` | PD 同机 |
| `AscendStoreConnector` | KV Pool | 跨实例 KV 复用 / 前缀缓存 |

PD 优化集群设计要点：P:D 比例靠压测；KV 传输路径尽量短；优先 Layerwise（逐层 push）；RoCE 必须无损（PFC + ECN）；关注 KV 传输耗时占端到端比例（>20% 说明传输是瓶颈）。

关键环境变量：`HCCL_IF_IP`、`HCCL_SOCKET_IFNAME`、`HCCL_RDMA_TIMEOUT=17`、`ASCEND_CONNECT_TIMEOUT`、`ASCEND_TRANSFER_TIMEOUT`。

昇腾侧限制：不支持异构 P/D 节点；非对称 TP 仅支持 `P_tp > D_tp` 且 `P_tp % D_tp == 0`；`engine_id` 必须唯一。

## 三、部署优化体系与验证机制

### 3.1 体系图（四层 + 一条主线）

主线：从 SLA 反推，而不是从算子往上堆。

```
SLA：TTFT / TPOT / 吞吐 / 成本          ← 先问"要达成什么"，再定"哪里动刀"
  ↓ 定约束
① 服务/调度层    batching、chunked prefill、prefix cache、PD 分离、KV 池
  ↓ 定并行度
② 并行/通信层    TP / DP / EP / PP 怎么选、通信量账、通算融合、HCCL/RoCE 与拓扑
  ↓ 定图
③ 图/模型层      算子融合、图捕获（ACL Graph）、模型结构接线、量化（权重/激活/KV）
  ↓ 定 kernel
④ 算子/硬件层    roofline 判瓶颈 → 达标率（带宽 ≥80% / MFU ≥70%）→ tiling / 流水 / 对齐
```

| 层 | 目标 | 主要手段 | 判据 | 项目里的落点 |
|---|---|---|---|---|
| ① 服务/调度 | 让 SLA 达标且资源不浪费 | continuous batching、chunked prefill、prefix cache、PD 分离、PagedAttention | TTFT / TPOT / 吞吐 / 显存占用，分开测分开报 | `deploy/` 完整部署方案（64 卡 / PD 分离 16 节点） |
| ② 并行/通信 | 装得下 + 通得动 | TP/DP/EP/PP 选择、MC2 通算融合、大 EP alltoall | 每 rank 专家数 vs 每 token 激活数；通信量 ÷ 互联带宽 | 896 专家 ÷ EP64 = 14 < 16 ⇒ 跨 rank 交换必然发生 |
| ③ 图/模型 | 少搬字节、能被调度 | 算子融合、图捕获、模型结构接线、量化 | 省的是 HBM 往返字节数；算子数；能否图捕获 | LatentMoE 图接线；`torch.ops` + `torch.compile` 图捕获 |
| ④ 算子/硬件 | 贴近硬件理论极限 | roofline 判瓶颈 → tiling / double buffer / 对齐 / 减少 Cast | 带宽达标率 ≥80%；MFU ≥70%；带归约的跟自己下限比 | SiTU-GLU / AttnRes 达标率 |

体系化的三个标志：

1. 同一件事在不同层判据不同——换层必须换判据。
2. 收益必须能跨层折算，且不能跨层相加——阶梯口径不能相加。
3. 瓶颈会迁移，要能说出下一个瓶颈在哪——K3 算子做到 80% 后，瓶颈在显存不在算力。

### 3.2 验证机制

"跑了一下、看对了"只是验证动作，不是验证机制。机制要能回答：判据哪来的？错了怎么发现？发现不了怎么办？

验证五件套：

| # | 机制 | 做法 |
|---|---|---|
| 1 | 判据先行 | 跑之前先把"通过"写死：数值 `±(atol + rtol·|ref|)`；性能 ≥80% / MFU ≥70% |
| 2 | 独立第二实现互证 | 两条互不依赖的路线各跑一遍，结论必须一致 |
| 3 | 负对照 / 反例 | 故意破坏一个前提，看指标是否按预期崩 |
| 4 | 证据分级 + 溯源 | 每个数字标"实测 / 可推 / 账面"；没跑的格子写"空着，别编" |
| 5 | 可复现 + 失败取证 | 一键脚本串起"编译→安装→对拍→失败留证" |

再加两条工程化机制：判据分层（单元 → 集成 → 系统，哪层缺就明说缺哪层）；回归与回退（关掉自研算子必须回到基线，假失败与真回归分开）。

AI 协作的定位：AI 出假设，验证机制裁决——每条结论都过五件套，不能因为"能跑"就认定它对。

### 3.3 诚实边界

| 项 | 状态 |
|---|---|
| 端到端 TTFT/TPOT | 未跑（`triton-ascend >= 3.2.1` 公开源暂无，外部包版本问题） |
| 融合算子（GEMM+SiTU） | 数值 PASS，但当前负收益（自写 GEMM tiling 只到峰值带宽 4%） |
| 相对华为算子的性能对比 | 华为无 SiTU-GLU / AttnRes，"相对提升"是假命题，正确对照是等价 torch 组合 |
| 更大规模验证 | 需 64 卡级集群；单卡/双机可做的已列成 L0~L4 阶梯 |
