# KIMI3 昇腾 A3 算子开发 设计·验证·测试报告

> 目标设备：昇腾 A3（Ascend 910_9382，SOC `ascend910_93`）· CANN 9.0.0 · torch_npu 2.10.0
> 交付范围：华为 CANN 尚未覆盖的 KIMI3 算子的 AscendC 实现 + 参考实现 + 验证 harness

---

## 1. 概述

### 1.1 背景

KIMI3 是 MoonshotAI 的混合架构大模型（MLA / KDA 线性注意力 + MoE）。在昇腾 NPU 上部署时，需要把模型里的每一层映射到 CANN 算子。经与华为 CANN 现有算子库比对，KIMI3 特有算子里有两类缺口：

1. 华为**完全没实现**的算子（需要从零写 AscendC kernel）；
2. 华为**有但形状/接口不匹配**、实际是图接线问题的算子。

### 1.2 交付物清单

| 类别 | 内容 |
|---|---|
| 自研 AscendC 算子 | SiTU-GLU（SituAndMul）、AttnRes 残差栈 |

## 2. 缺口分析

KIMI3 关键算子与华为 CANN 覆盖情况：

| 算子 | 华为覆盖 | 结论 |
|---|---|---|
| MLA attention | ATB `MultiLatentAttention` | ✅ 已有，无需开发 |
| MoE dispatch/combine | `npu_ops_transformer` | ✅ 已有，无需开发 |
| sigmoid 路由 + topk | ATB `FusedAddTopkDiv` | ✅ 已有，无需开发 |
| KDA（Gated Delta Rule） | `aclnnChunkKdaFwd` | ✅ 已有（本仓库补了 Python wrapper + 验证） |
| **SiTU-GLU** | ❌ 只有 SiLU | **自研 AscendC kernel** |
| **AttnRes 残差栈** | ❌ 无 | **自研 AscendC kernel** |
| **LatentMoE 投影** | ❌ 形状不符 | 🔧 图级组合（无需新 kernel，见 §7） |

**结论**：华为真正缺的算子只有 **2 个**（SiTU-GLU、AttnRes），本仓库均已实现并验证；LatentMoE 是模型图接线问题，不属算子开发。

## 3. 算子设计

### 3.1 SiTU-GLU（SituAndMul）

#### 数学定义（取自 MoonshotAI `modeling_kimi_linear.py` 的 `SituAndMul`）

输入 `x ∈ [..., 2d]`（前半 `gate`、后半 `up`），输出 `y ∈ [..., d]`：

```
gate = x[..., :d]      up = x[..., d:]
situ(gate) = beta * tanh(gate / beta) * sigmoid(gate)     # beta = 4.0
up'        = linear_beta * tanh(up / linear_beta)          # linear_beta = 25.0
y = situ(gate) * up'
```

与 SiLU（`x·sigmoid(x)`）不同：SiTU 是 **tanh·sigmoid 乘积**，且 up 分支还要 tanh 压缩。这是 KIMI3 特有的激活变体，华为只有 SiLU 融合。

#### 接口（aclnn）

```
aclnnSituAndMul(x, beta, linearBeta, out)
  x:        bf16 [..., 2d]
  beta:     double
  linearBeta: double
  out:      bf16 [..., d]
```

#### Kernel 设计

- **切分**：沿最后一维劈两半（gate = 前 d，up = 后 d）。
- **分块**：d 维按 `TILE_ELEM=4096` 分块，逐块处理，UB 占用可控。
- **计算**：内部 fp32，`Cast → Muls → Tanh/Sigmoid → Mul → Muls → Mul → Cast(bf16)`。
- **同步**：输入 DataCopy(MTE2)→向量(V) 与 向量(V)→输出 DataCopy(MTE3) 之间用 TQue 的 `EnQue/DeQue` 同步。
- **并行**：按 token 行数分到 8 个 core（blockDim=8）。

### 3.2 AttnRes 残差栈

#### 数学定义（取自 `_apply_attn_res`）

本质是「mini-attention」：对 B+1 个残差向量做 RMS-norm + 学习 score 点积 + softmax + 加权求和。

```
v = cat([block_residual, prefix_sum[:,None]], dim=1)     # (T, B+1, H)
k = v * rsqrt(mean(v^2, -1) + eps)                       # RMS-norm（H 维）
scores = sum(k * score_weight, -1)                       # (T, B+1)
probs  = softmax(scores, -1)                             # (T, B+1)
out    = sum(probs[:,:,None] * v, 1)                     # (T, H)
```

其中 `score_weight = norm.weight * proj.weight.squeeze(0) ∈ (H,)` 是学到的常量。

#### 接口（aclnn）

```
aclnnAttnRes(blockResidual, prefixSum, scoreWeight, eps, out)
  blockResidual: bf16 (T, B, H)
  prefixSum:     bf16 (T, H)
  scoreWeight:   bf16 (H,)
  eps:           double
  out:           bf16 (T, H)
```

#### Kernel 设计

- **两趟**：
  - Pass 1：逐残差向量算 `sum(v²)` 与 `sum(v·score_weight)`（沿 H 归约），得到 score，再 softmax（向量 `Exp` 在 32 对齐 buffer 上做）。
  - Pass 2：`out = Σ_b probs[b]·v[b]`（H 维逐元素累加）。
- **归约**：用 `ReduceSum(dst, src, workBuf, H)`，结果 `dst.GetValue(0)` 读标量。
- **并行**：按 token 分到 8 个 core。

## 4. 验证方法论

**无权重验证**：只靠 shape + 随机数据 + 参考实现验证算子正确性，不需要下载模型权重。

1. 从 KIMI3 config 拿 shape/dtype；
2. 固定 seed 生成随机输入；
3. 参考实现（纯 torch，fp32 内部 → bf16 输出）跑出 golden；
4. 待验算子（AscendC kernel，NPU 上）跑候选输出；
5. 对比：shape/dtype 一致 + 数值误差在容差内（bf16 用 max_rel < 1e-2）。

**为什么 golden 可信**：golden 是纯 `torch` 的直白实现，与 NPU kernel 完全解耦、不共享任何实现，作为正确性金标准。

## 6. 关键实现要点与坑

详见 `docs/02-AscendC算子开发流程与坑.md`，摘录最关键的：

1. **bf16 类型是 `bfloat16_t`**（`DT_BF16` 是宏 =27，不是类型）。
2. **`REGISTER_TILING_DEFAULT` 须在 `GET_TILING_DATA` 前**（它声明 `tilingData`）。
3. **跨引擎同步必须 `EnQue/DeQue`**（漏了 → 输出全零，这是最容易踩的坑）。
4. **标量 `exp` 在 aicore 上不存在**，softmax 用向量 `AscendC::Exp`。
5. **uint→float cast 不允许**，倒数类量移到 host 端算好传进 tiling。

## 7. 结论与后续工作

### 7.1 结论

- 华为缺的 2 个真算子（SiTU-GLU、AttnRes）**均已实现 AscendC kernel 并在 A3 上验证通过**，误差在 bf16 精度内。
- LatentMoE **不需要新 kernel**：它是图级组合 —— `down_proj(Linear H→moe_hidden) → MoE → [RMSNorm] → up_proj(Linear moe_hidden→H)`，全用现有算子（Linear=GEMM、MoE=npu_ops_transformer、RMSNorm、expert 内用本文的 SiTU-GLU）拼即可，属 vllm/sglang 适配层的图接线。

### 7.2 后续工作（建议由昇腾团队或部署侧完成）

1. **LatentMoE 图接线**：在 vllm-ascend / sglang 适配层插入 down/up 投影。
2. **性能 benchmark**：本报告只验证了正确性，未测 kernel 相对纯 torch 的吞吐/显存收益。
3. **算子合入**：若需合入 CANN，按 `docs/02` 的工程结构对齐规范即可。
