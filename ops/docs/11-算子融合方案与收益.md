# 两个算子怎么做融合（方案 + 收益 + 实现路径）

> 触发点：追问里被问「你的算子跟华为的比有什么优势」时，正确的答法是把话题从
> **单算子比拼**转到**融合深度**。这份文档就是那个"值得比"的方向的具体方案。
>
> ⚠️ **顺序前提**：融合必须排在单算子正确性之后。否则两个变量一起动，
> 精度出问题都分不清是 epilogue 写错还是融合边界写错。

---

## 1. SiTU-GLU：融进上游 GEMM 的 epilogue（**这是最值的一个**）

### 1.1 融合点在哪（源码位置是硬的）

```python
# modeling_kimi_linear.py:296-301
gate_up = torch.cat([self.gate_proj(x), self.up_proj(x)], dim=-1)   # [.., 2d]
down_proj = self.down_proj(self.act_fn(gate_up))                    # act_fn = SituAndMul
```

所以数据流是：

```
x ──┬─► gate_proj (H→d) ──┐
    └─► up_proj   (H→d) ──┴─► cat ──► SiTU-GLU ──► down_proj
                                    [.., 2d]      [.., d]
```

**关键事实**：`gate_proj` 和 `up_proj` 是**两个形状相同的 Linear**，输出被 `cat` 拼接。
而**我的 kernel 的输入格式恰好就是 `[..., 2d]`（前半 gate、后半 up）** —— 与 cat 的结果完全对齐。

### 1.2 融合方案：merged gate_up GEMM + SiTU epilogue

```
现在：  x → [W_gate; W_up] GEMM (H→2d) → 写回 GM → 读回 → SiTU → 写 out (d)
融合后：x → [W_gate; W_up] GEMM (H→2d) → 【L0C 结果直接做 SiTU】→ 写 out (d)
                                          ↑ 中间张量根本不落 HBM
```

为什么能合并成一个 GEMM：`cat([W_gate·x, W_up·x])` 等价于 `[W_gate; W_up] · x`
（权重按输出维拼接，一次矩阵乘直接得到 `[.., 2d]`）。vLLM / SGLang 里的
`merged gate_up_proj` 就是这个套路，所以**融合后的算子在框架里是有位置的**，不是自造的。

### 1.3 收益（可算，不用跑）

| 阶段 | 每 token 搬运的元素数 |
|---|---|
| 不融合 | GEMM 写 gate_up `2d` + SiTU 读 gate_up `2d` + SiTU 写 out `d` = **5d** |
| 融合后 | epilogue 直接算 + 写 out `d` = **1d** |
| **省掉** | **4d 个元素**（= `8d` 字节，bf16） |

代入 KIMI3 真实 `d = 11008`：

```
每 token 省 = 4 × 11008 × 2B = 88 KB
一层 MLP、3584 token       = 88 KB × 3584 ≈ 315 MB
```

> **这就是追问里那句「能比的是融合，不是单算子」的量化版**：
> 不需要任何未验证数字，`4d` 这个式子当场就能推。而且省掉的是**一次完整的写+读往返**，
> 属于"确定收益"，不是"可能更快"。

### 1.4 实现路径（AscendC）

用 **Matmul 高阶 API + 自定义 epilogue**，不是从零写 Cube：

```
① Matmul 部分：照搬现成的 —— A(x) 在 L1、B([W_gate;W_up]) 在 L1 → L0A/L0B → MAD → L0C
② 关键在拿 L0C 的方式：不用 IterateAll(直接落 GM)，而是
     matmulObj.Iterate(...)  →  matmulObj.GetTensorC(localC)   ← 拿到片上结果
③ epilogue：对 localC 做 SiTU-GLU 的向量链（就是现有 kernel 的 Compute 那段：
     Cast → Muls(invBeta) → Tanh → Sigmoid → Mul → Muls(beta) → 乘 up 分支 → Cast）
④ 写回：DataCopy 到 yGlobal(d)
```

**注意一个结构性变化**：现在我的 kernel 是"gate/up 各拷一块"，融合后
**gate 和 up 都在同一个 L0C tile 里**（因为一次 GEMM 出的就是 `2d`），
切分方式从"按 d 切成两块"变成"在 tile 内按 d 分两半"。这是实现上最容易写错的地方。

### 1.5 风险

| 风险 | 说明 |
|---|---|
| tiling 复杂度上升 | GEMM 的 BaseM/N/K 与 epilogue 的 tile 粒度要对齐，不能各算各的 |
| L0C 容量 | `BaseM × 2d × 4B` 要放得进 L0C(128KB) —— **`d=11008` 时不可能**，必须按 `2d` 方向再分块 |
| 精度 | epilogue 里多做一次 Cast 往返，要和独立算子版逐点对齐（用现有 harness 当 golden） |
| 调试难度 | 编译一次几分钟，出错时是 GEMM 问题还是 epilogue 问题要能二分定位 |

> **上机前先算 L0C 那条**：`d=11008` 意味着 `2d=22016` 个输出通道，
> 一次吃不下，必须沿 `2d` 分块 —— 这个约束会直接决定 tiling 怎么写。

## 2. AttnRes：**内部其实已经融了一部分**

### 2.1 源码里的真实形态

```python
# modeling_kimi_linear.py:1075
def _apply_attn_res(prefix_sum, block_residual, proj, norm):
#                                    ↑ 一个 nn.Linear    ↑ 一个 KimiRMSNorm
```

**AttnRes 不是一个纯 elementwise 算子 —— 它内部嵌了一个 RMSNorm 和一个 Linear(proj)。**
而我的实现在 `kimi3_ops/reference/attn_res.py` 里已经做了等价融合：

```
score_weight = norm.weight × proj.weight.squeeze(0)        # 两个权重先乘起来
scores = rsqrt(mean(v²) + eps) · (v · score_weight)        # RMS-norm 与投影折成一步点积
```

即：**RMSNorm + Linear(H→1) 被折成一次 H 维点积**，这就是"融合"，而且已经验证过
（`H=4096` 时 `max_rel ≈ 7.7e-3`）。所以对 AttnRes，"有没有做融合"的答案是**有**。

### 2.2 还能往哪融

| 方向 | 收益 | 难度 |
|---|---|---|
| **上游**：把残差生产者（attention 输出 / 上个 block 输出）直接写进 AttnRes 的输入 | 省一次 `H` 的写+读 | 高（要改生产者，耦合强） |
| **下游**：AttnRes 输出后若紧接 RMSNorm/Linear，把 norm 融进它的尾部 | 省一次 `H` 的写+读 | 中 |
| 内部：已经是融合态，没有更多空间 | —— | —— |

**结论**：AttnRes 的融合价值**主要在内部**（已完成），进一步融上游代价高、收益是 `H` 量级
（比 SiTU-GLU 的 `4d` 小，`d = 11008` vs `H = 4096`）。

## 3. 两个算子的融合价值对比

| | SiTU-GLU | AttnRes |
|---|---|---|
| 融合点 | **上游 GEMM 的 epilogue** | 内部（norm+proj 折成点积）✅ 已完成 |
| 每 token 省的搬运 | **4d 个元素**（= 8d 字节） | H 个元素（下游方向） |
| KIMI3 数值 | `d=11008` → **88 KB/token** | `H=4096` → 8 KB/token |
| 相对收益 | **大（差一个量级）** | 小 |
| 实现难度 | 中高（动 GEMM tiling） | 低（已做） |
| 价值 | **高** —— 正面回答"融合深度" | 中 —— 可作为"我已经做过一次融合"的例证 |

> **所以两件事都能做，但优先级很清楚：先做 SiTU-GLU 的 epilogue 融合。**
> AttnRes 那块的价值是"我已经融过一个（norm+proj 折点积）"，作为经验背书。

## 4. 动手顺序（别跳）

```
① 单算子跑通       build.sh + test_situ_real.py            ← 必须先过（当前未验证）
② 出单算子的数字    bench_situ_real.py --bench-bw-only 等   ← 建立基线
③ 写融合版 kernel   Matmul 高阶 API + SiTU epilogue
④ 用①的 harness 当 golden 对拍融合版（同一个参考实现，只是算子换了）
⑤ 量收益            对比 ② 的基线，看省的搬运有没有兑现
```

**每一步都有明确的验收点**，尤其 ④ —— 融合版最容易出的错是"GEMM 对了、epilogue 错了"
或反之，用同一份 golden 逐点比就能二分定位。
