## 5. ⚠️ CANN 9.0.0 的两个工程坑（本次实测）

### 5.1 `msopgen` 不接受中文路径

```
msopgen gen -i /workspace/华为昇腾算子/.../situ_glu_fused_op.json ...
  → [ERROR] The path .../华为昇腾算子/... is not valid
msopgen gen -i /tmp/sgf_op.json -out /tmp/sgf_gen
  → [ERROR] The path /tmp should not be written by user group or others, which will cause security risks
```

**两个硬限制**：① 路径不能含非 ASCII；② 输出目录不能是 777 权限。
（`build.sh` 走的是 cmake，不受此限——所以 SituAndMul / AttnRes 在中文路径下编译正常。）

### 5.2 Matmul 高阶 API 换位置了（旧模板配不上）

```
CANN 9.0.0：
  matmul_intf.h  →  aarch64-linux/asc/include/adv_api/matmul/matmul_intf.h   （仅此一处）
  TCubeTiling    →  aarch64-linux/asc/include/adv_api/kernel_tiling.h:305
  matmul_tiling.h→  aarch64-linux/asc/include/adv_api/matmul/matmul_tiling.h（host 侧）

而 msopgen 旧模板的 kernel include path 只含  tikcpp/tikcfw/
  → tikcpp 下已无任何 matmul 文件（find 结果为空）
```

**后果**：`SituGluFused`（融合算子）用 `#include "adv_api/matmul/matmul_intf.h"` 编译失败：

```
fatal error: adv_api/kernel_tiling.h: No such file or directory
```

**试过的补救（都无效）**：
- 顶层 `CMakeLists.txt` 加 `include_directories(.../asc/include)` → 对 kernel 编译不生效
- `op_kernel/CMakeLists.txt` 加 `npu_op_kernel_options(ascendc_kernels ALL OPTIONS -I...)` → 同样不生效

**结论**：融合算子要用 Matmul 高阶 API，得按 CANN 9.0 的**新工程模板**组织，
而不是 msopgen 的旧模板。这是**工程配置问题**，不是 kernel 代码问题——
`SituGluFused` 的设计与代码本身待验证，但**编译阻塞在模板/API 布局不匹配上**。

## 9. ★ 优化前后实测对比（**推翻了我自己文档里的一个论断**）

方法：造一个 baseline 工程（`kernels/SituAndMulBase/`），**只把三段改成串行、其余一字不改**，
用同一支 aclnn 直调程序（7 轮 × 50 次取中位）对比。控制变量。

| shape | baseline（三段串行） | 优化版（预取重叠） | 差异 |
|---|---|---|---|
| 3584×11008 | 0.4003 ms（达标率 81.5%） | 0.4005 ms（81.5%） | **+0.05%（噪声内）** |
| 512×11008 | 0.0622 ms | 0.0622 ms | 0 |
| 64×11008 | 0.0123 ms | 0.0123 ms | 0 |
| 1024×2048 | 0.0305 ms | 0.0312 ms | +2.3% |

### 结论（这是本次上机最值钱的一条）

**double buffer 在这个算子上没有可测量的性能收益。**

原因推断：**AscendC 的 TQue 本身就是引擎级流水** ——
MTE2（搬运）/ Vector（计算）/ MTE3（写回）分属不同硬件引擎，
`EnQue`/`DeQue` 是异步信号量而非完全阻塞；
原版的"串行"写法在**硬件层面已经重叠**了，代码层再加预取只是调整发射顺序。

### 因此要修正 `docs/04` 里的原话

> 原文写的是「depth=1 时 MTE2/V/MTE3 完全串行，三段的时间相加」——
> **实测不支持这个说法**（至少在这个算子、这个 shape、这颗芯片上）。
> 已把 `docs/04` 对应行改成实测结论。

### 那我的改动到底有价值吗？有，但不是性能

| 改动 | 性质 | 实测价值 |
|---|---|---|
| `tileElem` 由 host 按 UB 反推 | **可移植性** | 换 SOC/dtype 不用改 kernel 代码 |
| `blockDim` 查 AIV 核数 | **可移植性** | 换机器自动适配 |
| fp32 缓冲 4→3 块 | **UB 占用** | 数值上没改变实际 tileElem（都被 24B/元素 预算限制） |
| 任务粒度改 (row,tile) 均分 | **负载均衡** | 只在 `numRows % 核数 != 0` 时才有效 |
| `TQue` depth 1→2 | **（本次实测：无收益）** | —— |

### 怎么讲这段（比吹"我优化了"强十倍）

> 「我做了 double buffer 改造，但**实测对比后发现没有性能提升**——
> 串行版 0.4003ms、流水版 0.4005ms，几个 shape 下都一样。
> 我的解释是 **AscendC 的 TQue 本身就是引擎级流水**，搬运和向量计算分属不同硬件引擎，
> 代码层加预取只是调了发射顺序，硬件重叠本来就在发生。
> 所以我把它重新定位成**可移植性改造**（tiling 参数化、核数自动查询），而不是性能优化。
> **这个结论是测出来的——如果没做这个对比，我就会在追问里吹一个不存在的优化。**」

## 10. AttnRes 真机数据（`scripts/verify_attn_res_aclnn.cpp`）

### 正确性

| shape | max_abs | 纯相对误差 | **超容差元素** | 判定 |
|---|---|---|---|---|
| T=16 B=8 H=4096 | 1.41e-02 | 3.80e-03 | **0 / 65,536** | ✅ PASS |
| T=1024 | 2.98e-02 | 2.36e-02 | **0 / 4,194,304** | ✅ PASS |
| T=4096 | 3.09e-02 | 2.63e-02 | **0 / 16,777,216** | ✅ PASS |

**★ 附带收获：实测复现了「纯相对误差判据会假失败」** ——
T=1024 那行：纯相对误差判据给出 `2.36e-02 > 1e-2` 判 FAIL，
而标准判据 `±(1e-2 + 1e-2·|ref|)` 在 419 万个元素里 **0 个超容差**。
原因：`rel = err/(|gold|+1e-3)` 的分母在 `gold≈0` 时把 bf16 的正常绝对误差放大了。
**这就是 `docs/04` 里那条论断的真实证据**（判据必须带绝对项 `atol`）。

### 性能

| shape | 单次耗时 | 必要搬运 | 有效带宽 | 达标率 |
|---|---|---|---|---|
| T=16 B=8 H=4096 | 0.0146 ms | 1.25 MB | 89.9 GB/s | 7.4%（启动开销主导） |
| T=1024 | 0.2192 ms | 80 MB | 382.7 GB/s | **31.7%** |
| T=4096 | 0.9987 ms | 320 MB | 336.0 GB/s | **27.8%** |

**AttnRes 的带宽效率只有 ~28%**，原因不是 bug，是**算法结构**：
kernel 内部 Pass1/Pass2 各读一遍 `v`（共 2 遍），加上沿 H 的归约开销。
这正是 `docs/04 §7` 指出的浪费点（分块/驻留是它的下一步优化方向）。

### ★ 由此得到一个重要的判据修正

| 算子 | 类型 | 达标率 |
|---|---|---|
| SiTU-GLU | 纯 elementwise（1 读 1 写） | **81.5%** |
| AttnRes | 带归约 + 两趟读 | **27.8%** |

**「≥80% 达标」这条线只适用于纯 elementwise 算子。**
带归约的算子必须跟**它自己的理论上限**比（或用 roofline 判瓶颈），
不能一刀切 —— 否则会误判一个正确的归约算子"没优化好"。

### 5.3 追到根因（CANN 9.0 的两套编译模块）

```
compiler/tikcpp/ascendc_kernel_cmake/
├── ascendc.cmake       → 默认加载 legacy_modules（host_config/host_intf/function）
├── asc-config.cmake    → 加载 fwk_modules + asc_modules + FindASC.cmake
├── asc_modules/        → CMakeASCInformation.cmake：asc/include/**（含 adv_api/matmul）
└── legacy_modules/     → 旧路径 tikcfw（已无 matmul）
```

关键：`asc/include/**` 那一整套 include 出现在 **`ASC_CPU_SYSTEM_INCLUDE_OPTIONS`** 里 ——
它是给 **AscendC CPU 调试模式（`--run-mode=cpu` / tikicpulib）** 用的。
而 **NPU 编译（bisheng）走 legacy_modules → tikcfw，其中已无 matmul**。

⇒ **结论：CANN 9.0.0 的 AscendC C++ 工程（msopgen 模板）在 NPU 模式下，默认拿不到
Matmul 高阶 API 的 include 路径。这是工具链配置问题，不是 `SituGluFused` 的代码问题。**

补充事实：`/usr/local/Ascend/cann-9.0.0/asc` 是指向 `aarch64-linux/asc` 的**符号链接**，
所以 `$ASCEND_HOME_PATH/asc/include/adv_api/matmul/matmul_intf.h` 实际存在——
只是没被塞进 kernel 的编译命令行。

**三条可行路径**（按成本排序）：
1. 手工把 `$ASCEND_HOME_PATH/asc/include/adv_api/matmul` 等塞进 kernel 编译选项
   （`npu_op_kernel_options` 试过没生效，需查该宏接受的选项格式）
2. 改用 CANN 9.0 的 **ASC 语言**（`.asc` 走 `asc_modules`）—— 新工具链
3. 绕开高阶 API，用 tikcfw 的底层 Cube 接口手写（成本最高）

### 运行时失败的原因（已定位到方向）

```
Aicore kernel execute failed, fault kernel_name=SituGluFused_003206e0..._0
```

**UB 预算超了**：

| 占用 | 字节 |
|---|---|
| Matmul 的 `cTile`（baseM×baseN fp32 = 128×128×4） | 64 KB |
| 我的 5 个队列（g/u/tmp1/tmp2 各 baseM×subN×4=32KB + out 16KB） | 144 KB |
| **合计** | **208 KB** > UB 192 KB ✗ |

**修复方向**：减小 `subN`（队列随之变小）或让 epilogue 复用 Matmul 的输出 buffer
（`GetTensorC` 出来的 `cTile` 已经在 UB 里，不应再单独开 5 个队列）。

### 定性

**设计、工程结构、Matmul 集成、tiling 全部打通，只差最后的 UB 预算分配。**
这条修复路径是明确的（算清 UB → 调 subN 或复用 buffer），不是"不知道卡在哪"。

### 根因定性（★ 2026-09-19 更正：原结论是误判）

**原结论"本机没装 triton"错了。** 真根因见 §14.1：**工作区自己的 `kimi3_ops/triton/` 目录

### 所以：验证算子**完全不需要 torch_npu**

```
   ├── torch_npu 调它         ← Python 路线（本机缺 triton，需补环境）
   └── aclrt + aclnn 直接调    ← C++ 路线 ✅ 本次全部验证都走这条
```

### 13.1 根因①：`GetTensorC` 的 dst 是一个**从没被分配过的地址**

原 kernel：

```cpp
LocalTensor<float> cTile;      // ← 默认构造：没有绑定任何 UB 缓冲
while (mm.Iterate()) {
    mm.GetTensorC(cTile);      // ← 往空地址搬 L0C 结果
    ...
}
```

`LocalTensor` 默认构造 = **空地址**。官方融合算子样例（MatmulLeakyRelu）的写法是
**先从队列/TBuf 分配到 UB，再交给 `GetTensorC`**：

```cpp
while (matmulObj.template Iterate<true>()) {
    reluOutLocal = reluOutQueue_.AllocTensor<cType>();          // 必须先分配
    matmulObj.template GetTensorC<true>(reluOutLocal, false, true);
    ...
}
```

往空地址写 → 非法内存访问 → `ACL_ERROR_RT_AICORE_EXCEPTION (507015)`。
**这正好解释了 §11.1 的反常**：UB 账算出来只有 26 KB（≪ 192 KB）却照样崩——
不是"空间不够"，而是"这块空间从来没被分配过"。

### 13.2 根因②：C 的 `TPosition` 声明成了 `GM`，却用 UB 的方式取数

```cpp
using SitGluCType = MatmulType<TPosition::GM, CubeFormat::ND, float>;   // C 声明落 GM
...
mm.GetTensorC(cTile);        // 却要求 C 落 UB（VECIN）← 用法冲突
```

官方文档明确：**「取出 C 矩阵到 VECIN（UB）时，初始化要把 C 的逻辑位置设为 `TPosition::VECIN`」**；
C 设成 `GM` 时应走 `IterateAll(gmC)` 直接落 GM（那就没有 epilogue 了）。两者混用属 API 误用。
（产品支持差异：Atlas A3/A2 的 C 可用 `GM / VECIN / CO1`。）

### 13.3 根因③：host 侧没给 C 在 UB 上预留空间

原 host：`mmTiling.SetBufferSpace(-1, -1, -1)`（全默认）。融合算子场景官方要求**把 C 的 UB 占位
从 Matmul 可用 UB 里扣掉**：`SetBufferSpace(-1, -1, ubSize - usedUb)`，`usedUb = baseM × baseN × sizeof(float)`。
而 `baseM/baseN` 要 `GetTiling()` 之后才知道 ⇒ **必须二次 GetTiling**（先拿粒度、再带预留量重算）。

### 13.4 本轮改动（5 处）

| # | 文件 | 改动 |
|---|---|---|
| ① | `op_kernel/situ_glu_fused.cpp` | 新增 `TQue<QuePosition::VECIN, 1> cQueue`，`Init` 里 `InitBuffer(cQueue, 1, baseM*baseN*sizeof(float))` |
| ② | `op_kernel/situ_glu_fused.cpp` | 循环内改成 `cTile = cQueue.AllocTensor<float>()` → `GetTensorC(cTile)` → 循环末 `cQueue.FreeTensor(cTile)` |
| ③ | `op_kernel/situ_glu_fused.cpp` | `SitGluCType`：`TPosition::GM` → **`TPosition::VECIN`** |

| (2,7,256) d=128 | 0.0155 ms | 1.2 GB/s | 0.1% | 0.1149 ms | **7.43x** |

三条读法：

1. **大 shape 才是有意义的样本**：450 MB 搬运 → 0.4568 ms / 987 GB/s / **达标率 77.6%**，
   与 C++ 直调口径的 985 GB/s / 81.5%（§9）**互相印证**：两条独立路线的结论一致。
2. **小 shape 的"达标率低"不是 kernel 差**：那几组理论下限只有 0.0001~0.0012 ms，实测都在
   0.015~0.022 ms —— 被 **kernel 启动开销（~15-20 μs）** 主导。小 shape 的正确判据是"启动开销 + 搬运"。
3. **加速比 4.45x ~ 7.68x** 的分母是"等价的 torch 朴素组合"
   （`beta*tanh(gate/beta)*sigmoid(gate)*up'`，要落 3~4 个中间张量、多次 kernel 启动）。
   这是**唯一正确的基线口径** —— SiTU-GLU 华为根本没有，拿华为算子比是假命题（见 `benefit_total.py`）。

### 16.3 ⚠️ 代价：这一版**没有 HBM 收益**（必须说清楚）

C 落 workspace ⇒ `[M,2d]` 中间张量照样过一遍 HBM（还是 fp32，比不融合多一倍字节）。
所以重建版的定位是「**先把 MIX 通路跑通、把数值验对**」，不是收益版。
要省掉这次往返，得走阶段 2：照 `ffn_nonquant_nz.h` 的
`IterateAll` + `GetTensorC<false>(ubTensor)` 把 C 直接取进 UB（官方 FFN 正是这么把首个 GEMM 的 C 喂给激活的），
代价是同步更复杂（软同步 `SyncAll(syncGm, syncLocal)`）。

### 16.4.1 ✅ 已解决（2026-09-19 更正归因）：**重复执行**报 `507057` = **executor 复用**

现象：**第一次执行永远正确，从第 2 次起**失败：

```
rtStreamSynchronize: ErrCode=507057, desc=[suspect remote error]
设备侧：fftsplus aicore error, blk:2
        errorStr: The DDR address of the MTE instruction is out of range
```

`mssanitizer` 直接指出了方向：

```
Warning: Register FFTS_BASE_ADDR was not reset to default in block aiv(44)…(16)
         Expected default value is (0), but current value is (4398046396416)
```

**已排除的假设（都做了实测）**：

| 假设 | 实验 | 结果 |
|---|---|---|
| sys workspace 报小了 | host 改成 `libWs*2` | ❌ 反而变成挂住 |
| C 的尾部越界写 | C 后留 `baseN+512` / 留 64MB | ❌ 无效 |
| workspace 跨次残留 | 每次执行前 `aclrtMemset` 整个 workspace | ❌ 无效 |
| 空转核导致 KFC 状态不完整 | M=48（48 个 AIV 全有活） | ❌ 同样失败 |
| 分核与 tiling 不匹配 | 改 5 参 `SetOrgShape`（照官方 upsample） | ❌ 无效 |
| Matmul 集成模式 | 换官方 swiglu 的 **AIC 直执行**模式（不走 KFC） | ❌ 同样失败 |
| C 缓冲与 aclnn 的 tiling 区重叠 | C 缓冲往后挪 1 MB（host 相应加大 workspace） | ❌ 无效 |
| device 状态脏 | 换到**另一个 chip（device 1）**跑同样的 bench | ❌ 同样失败 |
| **我们的 kernel 逻辑** | **`Process()` 直接 `return`（空 kernel）** | ❌ **仍然 507057** |

⇒ **空 kernel 也复现** ⇒ 与本算子逻辑无关 —— 但**归因错了**：它不是"框架/驱动/环境层"的不可解问题，
   而是 **aclnn executor 不能被复用**。`GetWorkspaceSize` 一次 + 多次 `exec` 的写法里，
   第 2 次起 executor 内缓存的地址（`FFTS_BASE_ADDR` 那类寄存器基址）没有刷新，

### 16.6 ⏸ 阶段 2（C 取 UB 的真融合）：三种组合都试过，未通（已回退）

目标：让 `[M,2d]` 中间张量**不落 HBM**（大 M 时它占搬运量的 72%，见 §16.4.2）。
做法：`SetCType(VECIN)` + `Iterate` + `GetTensorC(cTile)` 把 L0C 结果取到 UB，直接在 UB 上做 epilogue。

| 试法 | 参考 | 结果 |
|---|---|---|
| `Iterate<true>` + `GetTensorC<true>(cTile)`（同步）+ 原样写回 workspace 验证 | —— | ❌ **数值 11% 错**（`1797/16384`，M=32 H=256 d=512）：取回的 tile 与"紧密 ND"的假设不符 |
| `Iterate<false>` + `GetTensorC<false>(cTile)`（异步，照官方 `ffn_nonquant_nz.h`） | `ffn.cpp:266`（`mmType<half, formatX, formatW, TPosition::VECIN>`） | ❌ **挂住**（无输出，timeout） |
| 改 host 侧同步项的其它组合（含给 C 预留 UB、`SetBufferSpace` + 二次 `GetTiling`） | 旧版经验 §13 | 同上，不改变结论 |

**修正一个此前的判断**：官方 FFN 那条路（arch32，用 `GetTensorC`）的 C 是 **`VECIN` + `CubeFormat::ND`**（`formatY` 默认 ND，只有显式 `-DFORMAT_Y=FRACTAL_NZ` 才是 NZ）
⇒ 所以"VECIN 只支持 NZ"不成立，**我的 ND 方向没错**，问题在**取回的 tile 的确切布局/对齐/尾块细节**。

**下一步的实测进展（同轮继续做了）**：

1. **直通 dump 实验**（kernel 里把 `GetTensorC` 的 UB 结果原样搬到 y，对拍程序用「C 的前 d 列」当 golden）：
   **约 80% 的位置读到 0**（每 8 列组都错 50-58 / 64）⇒ **不是"值错位"，而是"读到了未写入的区域"**

## 18. ★ 2026-09-19：算子层优化闭环 —— 用「变体对照」把 V 成本拆开，并真的把它降下来

> 触发：与 CANN 内置 `SwiGlu` 的同卡对测发现「我慢 2.31x」（`docs/17` §5、`docs/18` §2.3）。
> 本节记录的是从**归因 → 量化 → 证伪 → 有效优化**的完整闭环，每一步都有 msprof 数字。

### 18.1 归因：msprof 说它是**计算受限**（推翻了 `docs/04` §1 的假设）

同 shape `(8,512,22016)`、同卡：

| 算子 | dur | **aiv_vec_time** | **aiv_mte2_time** | 性质 |
|---|---|---|---|---|
| 内置 `SwiGlu` | 226.7 μs | 117.2 (52%) | **217.8 (96%)** | **访存受限** |
| 自研 `SituAndMul`（baseline） | 457.0 μs | **434.9 (95%)** | 107.7 (24%) | **计算受限** |

⇒ `docs/04` §1 那句「elementwise 必然访存受限 ⇒ 按带宽达标率判」**对超越函数密集的算子不成立**：`tanh`/`sigmoid`
吃的是 **V 指令吞吐**，而"脊点"是拿 **MAC 算力**算的 —— **不是同一个资源**。已在 `docs/04` 就地更正。

### 18.2 量化：用「故意做减法」把每个超越函数的成本拆出来

方法：临时改 kernel（源码备份在 `/tmp/situ_kernel_orig.cpp`），编译 → 安装 → msprof，**用差值反推成本**。
（改前先把 vendor 备份到 `/workspace/backup/`，可回滚。）

| 变体 | 改动 | dur (中位) | **vec** | mte2 | 结论 |
|---|---|---|---|---|---|
| **baseline** | 原版：2×Tanh + 1×Sigmoid | 457.0 μs | **434.9** | 107.7 | 计算受限 |
| **A** | 去掉 up 分支的 `Tanh` | 343.0 μs | **324.8** | 121.8 | **1 个 `Tanh` ≈ 110 μs** |
| **C** | 3 个超越函数全替换成 `Muls` | **240.1 μs** | **159.5** | **219.1** | 剩纯 Cast/Mul；**瓶颈当场迁移到搬运** |
| **D** | `Tanh` → `2σ(2x)−1`（形式变、**个数不变**） | 448.3 μs | 428.5 | 108.2 | **无收益 ⇒ 成本由「个数」决定，不是形式** |
| **E** | **2 个函数 → 1 个 `Exp`（β=4 快路径）** | **395.0 μs** | **374.0** | 113.6 | **-13.6%，对拍 PASS** |

**两条方法论收获（比数字本身更值钱）**：

1. **变体 C 的 dur（240.1 μs）≈ 内置 `SwiGlu` 的 226.7 μs**，且 mte2 几乎相同（219.1 vs 217.8）
   ⇒ **2.31x 的差距 100% 来自超越函数**，不是"我的搬运实现差"。
2. **瓶颈会迁移**（体系化认知的现场演示）：把 V 降下来后，mte2 从 24% 升到 **91%**，立刻变成新瓶颈。

### 18.3 有效的优化：Exp 复用（数学等价，仅对 β=4 成立）

原理（KIMI3 的 `activation_situ_beta = 4.0`）：

```
t = e^{−g/2}   ⇒   σ(g) = 1/(1+t²)          （1 个 Exp）
                    tanh(g/4) = (1−t)/(1+t)  （复用同一个 Exp）
```

⇒ gate 分支的 **2 个超越函数压成 1 个 `Exp` + 2 个 `Reciprocal`**。`β≠4` 时走通用回退（`if (beta == 4.0f)`）。

实测（同 shape）：

| 项 | 优化前 | **优化后** |
|---|---|---|
| dur（msprof 中位） | 457.0 μs | **395.0 μs（-13.6%）** |
| 有效带宽（bench） | 987 GB/s | **1142.7 GB/s** |
| **带宽达标率（大 shape）** | 77.6%（未达标） | **89.8%（达标 ✅）** |
| 加速比 vs 等价 torch 组合 | — | 7.16x |
| 与内置 `SwiGlu` 的耗时比 | 2.31x | **2.19x** |
| 对拍 | ALL PASS | **ALL PASS**（max_rel 8.438e-03） |
| `beta≠4` 回退路径 | — | ✅ 验证过（beta=3.0/9.0、8.0/50.0 均 < 1e-2） |
| **C++ 直调（独立第二实现，不经 torch）** | 0.4009 ms / 984.1 GB/s / 81.4% | **0.3461 ms / 1139.9 GB/s / 达标率 94.3%** |

> ★ **三条独立路径互证同一个优化**：
> C++ 直调 **-13.7%**（0.4009 → 0.3461 ms） / torch_npu 路线 **-13.6%** / msprof 的 `aiv_time` **-13.6%**（455 → 393 µs）。
> 三条路径**代码不同、调用栈不同**，都指向同一个结论 —— 这是"独立第二实现"的最强形式。

> ★ 那条 77.6% 的 FAIL **是靠优化消掉的，不是靠下调阈值**（阈值一直是 80%，见 `scripts/run_all_checks.sh` 的 `SITU_MIN_UTIL`）。

| 1 MB | 0.113 ms | 9.3 GB/s |
| 8 MB | 0.125 ms | 66.9 GB/s |
| 64 MB | 0.595 ms | **112.8 GB/s** |

⚠️ **边界与疑点（不许说过头）**：这是**同一张卡的 2 个 die**（HCCS 片内口径），
**不是跨卡、更不是跨机**；112.8 GB/s 与 A3 标称 **784 GB/s** 差 7 倍 ——
**要么标称是"超节点 NPU 间"口径不适用，要么通路有配置问题，目前未查清**。
⇒ 只当"通信层能测、正确性通过"的证据，**不当达标记**。跨机要 `hccn_tool -ping` / `ib_write_bw`（`docs/10` L1）。

### 19.3 两条"体系化"结论（比数字本身值钱）

1. **Amdahl 的实测版**：算子层大 shape 优化能让单算子快好几倍（§18），
   但**整机 TPOT 只改善 7.3%** —— decode 每步要读 **3.02 GiB 权重**（≈2.5 ms @1.2 TB/s），
   `act_fn` 只是其中一小块 ⇒ **"算子优化 ≠ 系统优化"**。
2. **同一个算子，在 prefill 与 decode 里的重要性完全不同**：TTFT 只差 **-0.1%**（prefill 是 GEMM 算力密集），
   TPOT 差 **7.3%** ⇒ 这正是"**换层要换判据**"的现场证据。

### 19.4 四层闭环（本节补上最后一层）

| 层 | 判据 | 实测证据 |
|---|---|---|
| **① 服务/调度** | TTFT / TPOT / 吞吐 / 显存 | **本节**：TTFT 12.17 ms、TPOT 6.60 ms、2433.7 tok/s（medium） |
| **② 并行/通信** | 通信量 ÷ 互联带宽 | **本节**：HCCL 2-die 64 MB busbw 112.8 GB/s（⚠️ 片内口径、待查） |
| **③ 图/模型** | 省的是 HBM 往返字节数 | L2 真实模型层：超容差 0/131072、整层 **1.69x** |
| **④ 算子/硬件** | 带宽达标率 / V 吞吐 | §18：达标率 **89.8%**、`aiv_vec_time` **93.5%**、优化 **-13.6%** |

### 19.5 局限（主动说）

- **不是 vLLM 端到端**（外部依赖阻塞），是自研 mini 引擎；
- 权重随机 + 规模缩小 ⇒ 数字反映**方法与比例**，不是 K3 真实性能；
- batch 内请求同长（真实引擎要 varlen kernel）；**PD 分离未实测**（需 ≥2 卡 + RoCE）。

## 20. ★ 2026-09-19：真权重分布鲁棒性 —— 收益倍数不是"随机数据上的假象"

K3 的真实链路是 `MXFP4 权重 → 软件反量化 →（动态 MXFP8 激活）→ SiTU-GLU`，
而 §9~§18 的数字都取自**随机高斯**输入 ⇒ 必须回答「**真权重下会不会退化**」。
脚本：`scripts/real_weight_robustness.py`（四类分布 × 三个 shape，d=11008 真实值）。

| shape | gauss（对照） | mxfp4（4bit 台阶） | outlier（通道×50） | mxfp4+outlier |
|---|---|---|---|---|
| `(128, 22016)` | 6.40x（9.005e-3） | 4.82x（7.748e-3） | 6.50x（8.724e-3） | 7.54x（7.748e-3） |
| `(512, 22016)` | 3.75x | 3.61x | 3.61x | 3.47x |
| `(2048, 22016)` | 3.69x | 3.63x | 3.69x | 3.64x |

（括号内为 `max_rel`；判据 `1e-2`，**12/12 全通过**）

**结论**：
1. **正确性不退化** —— MXFP4 往返后 `max_rel` 反而从 9.0e-3 降到 **7.748e-3**（量化后的值更规整）；
2. **加速比不退化**（3.47x ~ 7.54x）⇒ 收益倍数在类真实分布下依然成立；
3. outlier 不影响：`tanh`/`sigmoid` 本身会饱和，极值被压住。

**⚠️ 边界（别说过头）**：这做的是**输入分布**层面的贴近（模拟反量化台阶与 outlier），
**不是**加载真正的 K3 权重（1.5 TB / 96 分片，本机不具备条件）。
真权重到位后，`test_situ_real.py`（正确性）与本脚本（收益）可直接复跑。
