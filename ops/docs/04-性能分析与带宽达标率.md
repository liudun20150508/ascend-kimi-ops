# 性能分析与带宽达标率（昇腾 A3 / ascend910_93）

> 解决的问题：`设计验证测试报告 §7.2` 自述「未测吞吐/显存收益」，导致被问
> 「快多少」「tiling 怎么定的」答不上。本文给出**可复算的理论下限**、**达标率判定标准**、
> **实测方法**与**优化前后对照模板**。实测数字用 `bench_situ_real.py` 在 A3 上产出。

---

## 1. 为什么 elementwise 算子必须按「带宽」判合格

SiTU-GLU 每个输出元素只做十几次浮点运算，算术强度（Arithmetic Intensity, AI）很低：

```
AI = FLOPs / Bytes
```

对 bf16 的 SiTU-GLU，每个输出元素的搬运量固定：

| 流量 | 字节数（每输出元素） |
|---|---|
| 读 gate（bf16） | 2 |
| 读 up（bf16） | 2 |
| 写 out（bf16） | 2 |
| **合计** | **6 B** |

而计算量约 20~25 FLOPs（1 次乘、1 次除、tanh≈10、sigmoid≈5、2 次乘）。

```
AI ≈ 22 / 6 ≈ 3.7 FLOP/B
```

硬件的**脊点**（ridge point）= 峰值算力 / 峰值带宽。A3 上这个数在**数百**量级，
而 elementwise 的 AI 只有个位数 ⇒ **差两个数量级，必然访存受限**。

> 结论：这类算子的时间下限只有一个来源 —— 搬运字节数 ÷ HBM 带宽。
> 算力、指令条数、是否多用了一条 Cast，都不是决定项。

> ⚠️ **2026-09-19 实测更正（重要，别再用旧结论）**：上面「必然访存受限」的推理**对纯乘加算子成立，
> 对超越函数密集的逐元素算子不成立**。SiTU-GLU 实测（msprof，shape `(8,512,22016)`）：
> `aiv_vec_time = 434.96 μs`，`aiv_time = 465.27 μs` ⇒ **vec 占 93.5%**；而 `aiv_mte2_time` 只占 **22.5%**
> —— **它是计算受限的**。
>
> 错在哪：上面把 `tanh≈10`、`sigmoid≈5` 当成 **FLOPs 计数**，但那两个是**超越函数**，
> 在 V 单元上要展开成多条指令（`Exp` + 除法 + 多项式），吃的是 **V 指令吞吐**；
> 而"脊点"是用 **MAC 算力**算出来的 —— **两者不是同一个资源**，不能用它判超越函数密集的算子。
>
> ⇒ **判据要跟着瓶颈走**：访存受限看**带宽达标率**，V 指令受限看 **`aiv_vec_time` 占比**。
>
> 同 shape 实测对照（`docs/17` §5）：内置 `SwiGlu`（只 1 个 sigmoid）`mte2 占 96%` ⇒ 访存受限；
> 自研 `SituAndMul`（2×Tanh + 1×Sigmoid）`vec 占 93.5%` ⇒ 计算受限。

## 2. 理论下限与达标率

```
搬运字节数 N = numRows × (2d + 2d + d) × 2B = numRows × 6d  (B)
理论下限时间 T_min = N / BW_peak
实际有效带宽 BW_eff = N / T_measured
达标率 = BW_eff / BW_peak × 100%
```

以 KIMI3 真实 `intermediate_size d = 11008`、`numRows = 3584`（一层 MLP 的 token 数）为例：

```
N = 3584 × 6 × 11008 ≈ 236.6 MB
若 BW_peak = 1600 GB/s（占位值，必须实测替换）
T_min ≈ 236.6e6 / 1600e9 ≈ 0.148 ms
```

**判定标准（问答可以直接背这句）：**

| 达标率 | 判定 | 典型原因 |
|---|---|---|
| ≥ 80% | 优化到位，可以停 | —— |
| 60 ~ 80% | 还能抠，但边际收益下降 | tile 偏小、尾块不齐、核数没用满 |
| < 60% | 有问题，必须查 | 流水没重叠（TQue depth=1）、多做 Cast 往返、访存未对齐、逐行串行 |

> 「**达不到 80% 就是没优化到位**」——这句话就是对方想听的"你会不会量化自己的工作"。

## 3. 这次改了哪四处（对应达标率提升）

改造前 `op_kernel/situ_and_mul.cpp` 的四处结构性缺陷：

| # | 改造前 | 改造后 | 为什么影响达标率 |
|---|---|---|---|
| 1 | `TQue<..., 1>` 队列深度全是 1 | `QUEUE_DEPTH = 2`（double buffer） | ⚠️ **实测推翻了这里的原假设**（见 `docs/14` §9）：串行版 0.4003ms vs 流水版 0.4005ms，**无可测收益**。原因：AscendC 的 TQue 本身就是引擎级流水——MTE2/MTE3 与 Vector 分属不同硬件引擎，天然可并行；代码层加预取只是调整发射顺序。**这一项应定位成「可移植性改造」，不是「性能优化」** |
| 2 | `TILE_ELEM = 4096` 编译期常量 | host 端查 UB 容量反推 `tileElem`，写进 tiling | 硬编码换个 SOC / dtype 就废；现在按 `UB / 2 / 24B` 反推，dtype 变了自动跟着变 |
| 3 | 每个 tile 用 4 块 fp32 缓冲（gate/up/tmp1/tmp2） | 3 块（gate 分支用完的 `acc` 复用给 up 分支） | UB 占用从 22 B/元素降到 24 B/元素预算下的 3 块 → 同样 UB 能放下更大的 tile，减少循环次数与启动开销 |
| 4 | `rowsPerCore = numRows / blockDim` 按**整行**均分 | 按 **(row, tile) 分块**展平均分 | 行数不是核数整数倍时，尾核空转、其余核多跑；改成 tile 粒度后长尾从「一行」缩到「一个 tile」 |

补充：`1/beta`、`1/linear_beta` 也从 kernel 内移到 host 端算好传进来（aicore 上 uint→float cast 受限，且省掉每 tile 一次除法）。

**UB 预算口径（写进 host tiling 的依据）：**

```
输入 gate 队列 depth=2 × bf16 : 2 × 2 = 4 B/元素
输入 up   队列 depth=2 × bf16 : 2 × 2 = 4 B/元素
输出 out  队列 depth=2 × bf16 : 2 × 2 = 4 B/元素
片内 fp32 计算缓冲 3 块 × 4B  :        12 B/元素
──────────────────────────────────────────────
合计                                 24 B/元素（tileElem = UB × 0.5 / 24，向下对齐 256）
```

## 4. 怎么实测（`bench_situ_real.py`）

```bash
# 1) 先测本机真实峰值带宽，别用占位值
python bench_situ_real.py --bench-bw-only
#   → [峰值带宽] copy 512MB×2: 0.6xx ms → 1xxx GB/s

# 2) 再用实测峰值跑达标率
python bench_situ_real.py --peak-bw 1600
```

脚本输出每组 shape 的：理论下限 ms、自定义算子 ms + GB/s + 达标率、torch 算子组合基线、加速比。

> **基线怎么选很重要**：拿 `beta*tanh(gate/beta)*sigmoid(gate)*up'` 这种 torch 表达式当基线
> （而不是拿另一个手写 kernel），因为它就是「没有自定义算子时」的真实成本 ——
> 至少要落 3~4 个中间张量到 HBM。这才是融合收益的正确度量。

单 kernel 拆解（想看 MTE2 / V / MTE3 各占多少，用来验证「流水到底重没重叠」）：

```bash
msprof --application="python bench_situ_real.py" --output=./prof --ai-core=on
# op_summary 里看 situ_and_mul 的 aiv_time、mte2_time、vec_time、mte3_time 占比
# 若 mte2_time + vec_time + mte3_time ≈ aiv_time（即三段相加），说明流水没重叠
# 若 ≈ max(三者)，说明 double buffer 生效
```

## 5. 没达到 80% 的排查树

```
达标率低
├── 先看 msprof：mte2 + vec + mte3 是否 ≈ aiv_time？
│   ├── 是 → 流水没重叠：确认 TQue 深度 ≥2、AllocTensor/EnQue 是否放在循环外提前发
│   └── 否 → 看是谁的占比最大
│        ├── mte2 高 → 搬运效率问题：DataCopy 是否 32B 对齐、长度是否够大写满 burst
│        ├── vec 高  → 计算成了瓶颈：正常现象（说明已经不是纯带宽受限），或 Cast 往返过多
│        └── mte3 高 → 写回没和计算重叠
├── tile 太小？ → 每组 shape 试 3 档 tileElem，看达标率拐点（通常 4K~16K 元素）
├── 核数没用满？ → 打印 blockDim 与总 tile 数，确认 tilesPerCore > 0 且末核有活
└── 对齐问题？   → bf16 要求 16 元素（32B）对齐；d 不是 16 的倍数时尾块会退化
```

## 7. AttnRes 的测法（同类思路，瓶颈不同）

AttnRes 不是纯 elementwise：它是 B+1 个 H 维向量做 RMS-norm + 点积 + softmax + 加权和，
有 **ReduceSum 归约**和**两趟遍历**。它的下限时间按「每 token 的访存字节数 ÷ 带宽」算：

```
每 token 流量 = (B+1) × H × 2B × 2（Pass1 读一遍 + Pass2 再读一遍） + H × 2B（写）
             = (B+1) × H × 4 B + 2H B
```

Pass1 / Pass2 各读一次 `block_residual` 是它的主要浪费点 ——
想再快就得把 v 缓存在 UB 里一趟做完（受 UB 容量限制），这是它的下一步优化方向，不是 double buffer 能解决的。
`H=4096, B=16` 时单 token 需 4096×2×17×2 ≈ 557 KB，远超单核 UB（192KB），所以只能分块或复读。

**实测（A3，`docs/14` §10）**：T=4096 时 0.9987 ms、有效带宽 336 GB/s、**达标率 27.8%**，且 0 个元素超容差。
低的不是“没优化好”，而是两趟读 v 的结构开销 —— 所以 **≥80% 这条线只适用于纯 elementwise 算子**，
带归约的算子要跟它自己的理论上限比（或用 roofline 判瓶颈）。

## 9. 工具链：`msprof` 是什么，以及它的对标（被问"你怎么剖析"时看这节）

`msprof` 是 **CANN 自带的性能分析工具**（路径 `/usr/local/Ascend/cann-9.0.0/bin/msprof`），
属于华为 **MindStudio** 工具链，**不依赖 PyTorch、也不是第三方**。同族工具（本机 `tools/` 下都有）：

| 昇腾 | NVIDIA 对标 | 干什么 | 我们用过吗 |
|---|---|---|---|
| **`msprof`** | `nsys` + 部分 `ncu` | 时间线 + 算子级统计（本项目的**主力**） | ✅ 全部关键结论 |
| `msopprof` | `ncu` | 单算子深度剖析 | — |
| **`mssanitizer`** | `compute-sanitizer` | 内存越界 / 竞争 / 未初始化 | ✅ 定位过 `507057` |
| `msdebug` | `cuda-gdb` | device 侧调试 | — |
| `msaicerr` | — | AI Core 错误的符号化解析 | — |
| `operator_cmp` | — | 算子精度对比（对拍的官方工具） | — |
| `msopgen` / `tikcpp` / `bisheng_compiler` | `nvcc` 工具链 | 算子工程生成 / AscendC 框架 / 编译器 | ✅ 编算子 |

**它采到的字段（这才是关键）**：`op_summary` 里按 **CUBE（`aic_*`）** 与 **VECTOR（`aiv_*`）** 两套分别给
`mac / scalar / mte1 / mte2 / mte3 / fixpipe / vec / icache_miss_rate` 的**时间与占比**，外加 `Task Duration`、`Block Num`。

⇒ 于是"**计算受限还是访存受限**"不是猜的，是**读出来的**：

| 算子 | 实测 | 判定 |
|---|---|---|
| 自研 `SituAndMul` | `aiv_vec_time` **93.5%** | **计算受限**（→ 该降指令数，不是调 tiling） |
| 内置 `SwiGlu`（同 shape） | `aiv_mte2_time` **96%** | **访存受限**（→ 该调搬运/tiling） |

本项目的关键结论全部出自它：§9 的达标率、§14.3 的加速比、§16 的融合算子定位、
§18 的**变体对照实验**（baseline/A/C/D/E 每个数字）、§20 的真权重鲁棒性。

> **话术**：「性能剖析我不靠感觉：昇腾上用 `msprof`（对标 `nsys`/`ncu`）拿算子级 `aic_/aiv_` 分段，
> 靠 `aiv_vec_time` 与 `aiv_mte2_time` 的占比判定**计算受限还是访存受限** —— 这直接决定我改什么：
> 访存受限调 tiling/对齐，计算受限降指令数。内存问题用 `mssanitizer`（对标 `compute-sanitizer`）。
> **判据跟着瓶颈走，而瓶颈是先测出来的。**」

## 10. 术语：「baseline / 基线」在本项目里有**四种**用法（别混）

**核心原则**：**baseline 不是某个固定对象，而是"回答某个问题时选定的对照物"。**
报任何收益数字之前，先说清「**它的 baseline 是谁**」。本项目实际用过四种：

| # | 出现处 | baseline 是什么 | 它回答的问题 | 结果 |
|---|---|---|---|---|
| ① | `docs/14` §9（`kernels/SituAndMulBase/`） | **串行版 kernel**（去掉 double buffer，三段串行，其余一字不改） | **double buffer 有没有收益？** | ❌ **没有**（0.4003 vs 0.4005 ms，噪声内） |
| ② | `docs/14` §18（变体实验） | **原版 kernel**（优化前：2×Tanh + 1×Sigmoid） | **变体优化收益多少？** | ✅ 457 → **395 µs（-13.6%）** |
| ③ | `bench_situ_real.py` 的 `torch 算子组合(基线)` | **等价 torch 组合**（6 个 elementwise） | **收益倍数是多少？** | ✅ **3.5~7.5x** |
| ④ | `scripts/baseline_twostage_aclnn.cpp` | **两段式（不融合）**：内置 `MatMulV2` + 自研 `SituAndMul` | **融合有没有收益？** | ❌ **负收益**（812.6 vs 44.2 µs） |

**唯一"固定"的基线是 ③**：它是**收益倍数的分母**，永远是「**等价功能的朴素实现**」——
**不能换成华为的算子**（华为没有 SiTU 变体，换分母就是假命题，见 `docs/17` 口径 A）。

> ⚠️ **同样的算子，对不同 baseline 的结论完全不同**：我的 `SituAndMul` 对 ③ 是 **3.5x**，
> 对 ④（融合对照里的零件）是"两段式的一部分"，对 ① 是"**没差别**"。
> ⇒ 被问"快多少 / 有没有收益"时，先在心里补一句：**"baseline 是谁？"** —— **答错分母 = 答错题。**
