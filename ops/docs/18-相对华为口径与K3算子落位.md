# 18 - 两问的答卷：相对华为口径 + 用我的算子部署 K3

> 触发场景：对方问了两句 ——
> ① 「**你比华为开发的昇腾提升多少？**」
> ② 「**K3 怎么部署？既然是部署肯定要用你开发的新算子，给个方案。**」
>
> ⚠️ **场景澄清（别读混）**：这里的「华为」是**对比对象**
> —— 华为的昇腾 / CANN 内置算子与官方部署 recipe，**不是对方**。
> 本文简称的「相对华为口径」= 与华为自家昇腾做对比时的分母与证据口径。
>
> 这两问**不是一回事**：①是**口径问题**（分母选错就是假命题），②是**方案问题**（要的是落位与验收，不是"跑给我看"）。
> 本文把两问的答案收成可背的一页，并回答"那个红色 ❌（在 vLLM/SGLang 里真跑起来）到底要不要做"。
>
> 关联：`docs/17`（收益三层账 + 相对华为三分）、`docs/12`（算子怎么进 vLLM/SGLang 的三层机制）、
> `../integration/README.md`（接入层现状与端到端卡点）、`../kimi3_deploy/KimiK3-昇腾部署方案.md`（部署方案本体）。

## 0. 先看结论（三句话）

1. **红色 ❌ 不值得当成交付项**：它在**当前机器**上不可做，卡的是**外部版本**（下面 §1.1 三条硬事实），
   而且它证明的是「框架装得起来」，不是「算子做得好」。对方要的两问，**都不靠它回答**。
2. **问①正确答法是换分母**：华为**没有** SiTU-GLU / AttnRes，拿"华为算子"当分母是假命题；
   分母必须是「等价的 torch 朴素组合」（**4.45x~7.68x**，达标率 **81.5%**）。
   唯一能和华为**直测**的是 KDA（精度对齐 ~4.4e-3，**无性能优势可吹**），
   以及**同属 GLU 家族的 `SwiGlu`**（只能比带宽达标率）—— 这一格原来空着，§2.3 给了补测脚本。
3. **问②的答案是"落位 + 装载链路 + 验收"**，不是"我把它跑起来了"：K3 部署走**官方镜像 + 官方 recipe**，
   我的算子以**补缺算子 + 图接线**的形式挂进去（§3 的落位表），收益按 `docs/17` 的三层账说，**只对 prefill 成立**。

## 1. 那个红色 ❌：到底要不要做

### 1.1 三条硬事实（复核命令在手，别凭印象）

| # | 事实 | 证据 |

> 顺带更正一处旧口径：`vllm-ascend 0.20.2~0.22.1` 要的 `torch-npu` 就是本机的 **2.10.0**（版本代际本来就匹配），
> 当年"钉死 2.5.1"的说法只适用于 `0.9.x`。**真正的卡点从头到尾只有一个包：`triton-ascend >= 3.2.1`。**
> 更详细的过程见 `docs/14` §15.3 与 `../integration/README.md` §3。

### 1.2 那这一格该由什么证据回答？（四层证据阶梯）

| 层 | 要证明什么 | 证据 | 状态 |
|---|---|---|---|

**读法**：被问的「**集成进昇腾框架没有**」，①~③ **全部能答"有，且是实测数字"**；

**⚠️ 别把 ④ 的空缺说成"算子没集成"** —— 那会把一个**环境包版本问题**，说成**自己的算子问题**，是白送的减分项。

### 1.3 真要打这一格，什么时候打、怎么打

**前置条件（任一）**：拿到 `triton-ascend >= 3.2.1`（华为官方渠道 / 配套镜像）、或把 CANN 升到 **9.1.0** 且用 `vllm-ascend 0.23.0`。

**环境就绪后的执行清单**（照做，30 分钟量级）见 `../integration/README.md` §4：
确认三者版本配套 → 装框架 → 打两处补丁（注册 + 模型里换 `act_fn`）→ tiny 模型冒烟 → 量 TTFT/TPOT。

**上机前可先做的两件"零风险"准备**（本机就能做，不需要 vLLM）：
1. `python3 ../scripts/bench_swiglu_vs_situ.py` —— 把"相对华为"那一格填上（§2.3）；
2. 用 `../integration/vllm_situ_glu.py` 里的 `SituAndMulModule` 在 **pure torch** 下跑一遍 MLP 前向，
   确认"替换后数值不变"（这一步已经在 L2 里做过，`1.75x` 那个数就是这么来的）。

## 2. 问①「比华为提升多少」——答法与补测

### 2.1 对方这句话有两种读法，**两种都要接**

| 读法 | 他其实在问 | 答法 |
|---|---|---|
| **(a) 算子 vs 华为算子** | 你的 kernel 比 CANN 内置的同类快多少 | 华为**没有** SiTU-GLU/AttnRes ⇒ 换分母（等价 torch 组合）；能直测的只有 KDA 与 `SwiGlu`（§2.2、§2.3） |
| **(b) 我的方案 vs 华为的 K3 昇腾适配** | 官方路径之外，你能加什么 | 官方 recipe 用 CANN 内置算子；**我加的是"补缺 + 融合 + 接线"三件官方没有的东西**（§3.1 落位表） |

只答 (a) 会把问题答小；只答 (b) 会被追问"数字呢"。**两句一起说**：先换分母给数，再说我加的是什么。

### 2.2 现成的数字（全部实测，出处见 `docs/17` §6 溯源表）

| 项 | 数字 |
|---|---|
| SiTU-GLU 达标率（C++ 直调） | **81.5%**（0.4003 ms / 985 GB/s；该卡实测峰值 1208.7 GB/s） |
| SiTU-GLU 加速比（vs 等价 torch 组合） | **4.45x（大 shape）~ 7.68x（小块）** |
| AttnRes 正确性 / 达标率 | **0/16,777,216** 超容差 / 27.8%（结构决定，非 bug） |
| KDA vs 华为 `aclnnChunkKdaFwd` | 精度对齐 **~4.4e-3**；**无性能优势可吹**（如实说） |
| 整层 MLP（官方 `KimiMLP` 同权重） | 超容差 **0/131,072**，**1.75x** |
| 收益账（每 token 省的 HBM 往返） | `12d + 4d + 8(B+1)H` ≈ **920 KiB/token**；prefill 4096 token 每层 ≈ **3.2 ms**（估算，除带宽得出） |

**必带的两句限定**（不带就是把估算说成实测）：
- 省的是 **HBM 往返不是时间**，换时间要除带宽；
- 收益**只对 prefill 放大**（decode 每步要读整层权重 ≈1.38 GB，省的 920 KiB 占 **0.065%**，可忽略）。

### 2.3 ★ 已实测：与 CANN 内置 `SwiGlu` 的同卡同判据对测

**为什么是这一格**：华为的 GLU 家族里有 `SwiGlu`/`SwiGluQuant`/`ClippedSwiglu`/`GeGlu`/`Glu`，
**没有 SiTU 变体**（激活数学不同：SwiGLU 是 `silu(gate)·up`，SiTU 是 `β·tanh(g/β)·σ(g)`）。
所以两者**不能比"谁算得对"**，**只能比"带宽达标率"** —— 同一个 shape、同一张卡、同一套计时口径。

**怎么测（本机就能跑，脚本已给）**：

```bash
cd kimi3_ops
/usr/local/python3.11.15/bin/python3 scripts/bench_swiglu_vs_situ.py --bench-bw-only   # ① 先测本卡峰值带宽
/usr/local/python3.11.15/bin/python3 scripts/bench_swiglu_vs_situ.py                   # ② 同 shape 对测两个算子
```

脚本会把三行打在一起：**内置 `npu_swiglu` 的达标率 / 我的 `situ_and_mul` 的达标率 / 峰值带宽**，
搬运字节按"读 gate(2d) + 读 up(2d) + 写 out(d)"统一口径算 —— 这样两个数**可以并排说**。

**★ 实测结果（2026-09-19，A3 真机）**：

| shape | 内置 `npu_swiglu` | 自研 SiTU-GLU | 比 |
|---|---|---|---|
| `(8,512,22016)` d=11008 | **0.1980 ms** | 0.4570 ms | 自研慢 **2.31x** |
| `(2,7,22016)` | 0.0237 ms | **0.0200 ms** | 自研快 1.18x |
| `(2,7,4096)` | 0.0239 ms | **0.0184 ms** | 自研快 1.30x |

**归因（msprof 同 shape 对照）**：

| 算子 | dur | **vec（计算）** | **mte2（读搬运）** | 性质 |
|---|---|---|---|---|
| 内置 `SwiGlu` | 226.7 μs | 117.2 (52%) | **217.8 (96%)** | **访存受限** |
| 自研 `SituAndMul` | 469.4 μs | **434.96 (93.5%)** | 104.7 (22%) | **计算受限** |

⇒ **2.31x 主要来自数学成本**（SwiGLU 只要 1 个 sigmoid；SiTU 要 2×Tanh + 1×Sigmoid + 1×Div，
而且全程 fp32 ⇒ 3 次 Cast），**不是我搬运实现差**；但 `aiv_vec_time` 占 93.5% 也说明 **V 指令数还有得降**。

**现成话术（照念）**：

1. 「大 shape 下内置 SwiGLU 比我快 **2.31x**，我如实报 —— 但两者**数学不同**：它只要 1 个 sigmoid，我要 2 个 tanh + sigmoid + 除法。」
2. 「差别我用 msprof 定到了**资源上**：我的 `aiv_vec_time` 占 **93.5%**，内置是 `mte2` 占 **96%** —— **一个计算受限、一个访存受限**，判据也不同。」
3. 「所以下一步不是调 tiling（那是访存受限的活），而是**降 V 指令数**：β=4 时 `tanh(g/4)` 与 `σ(g)` 能共用一次 `Exp` + 一次 `Sqrt`，或用多项式近似替掉 `Exp`。目标：把 V 时间压到 ≤220 μs，让访存重新成为瓶颈。」
4. 口径诚实：「内置按带宽口径算出 **179%**，说明 copy 峰值（1:1 读写）不能给读多写少的算子当分母 —— 我只报同口径的时间比。」

**（旧）三种情况怎么读**（脚本仍会打印，保留备查）：

| 结果 | 话术 |
|---|---|
| 我的 ≥ 内置 | 「同类 GLU 算子同卡同判据下我没输」，再补一句"内置算子还能吃量化（`SwiGluQuant`），我目前只有 bf16" |
| 我的略低（3~10 个点） | 「差在 tiling 硬编码与多余 Cast（`docs/14` §缺口清单），下一步是把 `TILE_ELEM` 移到 host 端按 UB 容量自适应」——**给出改进项比编一个更高的数强** |
| 内置明显高（>20 点） | 如实说"我的 kernel 还没吃满带宽"，不要改判据、不要挑小 shape 糊弄 |

> ⚠️ **不许做的事**：拿 SiTU 的达标率去和 SwiGLU 比"谁准"；拿小 shape 的达标率（1.5%）去和内置比
> （小 shape 是被启动开销主导的，判据要换成"启动开销 + 搬运"，见 `docs/04`）。

### 2.4 30 秒话术（背这段）

> 「跟华为比要分三种。**SiTU-GLU 和 AttnRes 华为没有** —— CANN 的 GLU 家族只有 `SwiGlu`/`GeGlu`/`Glu`，
> 没有 SiTU 变体，所以给的是**补缺**，分母只能用「等价的 torch 组合」：加速比 **4.45x~7.68x**、带宽达标率 **81.5%**。
> **能跟华为直测的只有 KDA**，我跟 `aclnnChunkKdaFwd` 对拍差 **4.4e-3**，**精度内、没有性能优势可吹**。
> **真正值得比的是融合深度**：华为在 MoE 的 GMM 场景做了 `GroupedMatmulSwigluQuant`，
> dense 侧华为有 `aclnnFFNV3`（`y=act(xW1+b1)W2+b2`），**但 activation 只到 swiglu/geglu/reglu，不含 SiTU**；
> 我补的是**这一种激活**，省的是 `[M,2d]` 那次写 + 读，**4d 个元素 = 88 KB/token**。
> 省的是 **HBM 往返不是时间**，换算要除带宽，而且**只在 prefill 放大**，decode 相对整层权重读取不到千分之一。」

**追问预案**（能提前防住三个坑）：

| 追问 | 答法 |
|---|---|
| 「那到底快多少？给个数」 | 补缺那块有实测（4.45x，分母是等价 torch 组合）；**融合那块目前是负收益，我如实讲**（见下） |
| 「融合算子跑通了吗？」 | 「**能跑对**（4 组 shape 全 PASS，含真实 `d=11008`），**但当前是负收益**：812.6 μs vs 内置 `MatMulV2` 39.88 μs，因为**我自写的 GEMM tiling 只跑到峰值带宽 4%**。要拿收益，前提是先把 GEMM 做到能和内置打平 —— 否则是给爆胎的车换雨刷。」 |
| 「为什么不用华为算子当分母？」 | 口径 A：华为没有 SiTU-GLU，拿它当分母是假命题；清单里"没有"也只是**弱证据**（分类 JSON 不是全量枚举），真正的强证据是仓库里的真机对拍 |

## 3. 问②「K3 怎么部署，用你的算子」——方案

### 3.1 我的算子在 K3 里的落位（对着模型结构说，不讲空话）

| K3 结构（`kimi3_deploy` §1.1 的规格） | 官方路径怎么算 | 我的交付物 | 接入层 | 状态 |
|---|---|---|---|---|
| **dense MLP 的 SiTU 激活**（93 层里那 1 层 dense + 每层 MLP 形态） | CANN 只有 `SwiGlu`/`SiluAndMul`，**没有 SiTU** | `torch.ops.kimi3_ops.situ_and_mul` | 模型文件里把 `act_fn` 换掉（`integration/vllm_situ_glu.py`） | ✅ 真机验证（含图捕获） |
| **MoE 专家内的 activation**（896 专家 / 激活 16） | 官方 `GroupedMatmulSwigluQuant`（GMM 场景） | 同上（SiTU 版） | 专家 FFN 的 activation 处 | ✅ 算子在，接线在 `integration/latent_moe.py` |
| **Latent MoE 的 down/up 投影**（3584 维 latent） | 官方形状不符 ⇒ **要接线** | 无新 kernel，**图接线** | 在 MoE 前后加 `down_proj`/`up_proj` + norm | ✅ 与官方 `KimiSparseMoeBlock` 同权重 **0/384** |
| **Attention 残差栈**（69 层 KDA + 24 层 Gated MLA） | 官方 KDA 有 `aclnnChunkKdaFwd` | `torch.ops.kimi3_ops.attn_res` | attention 输出侧的残差融合 | ✅ 真机对拍 0/16,777,216 |
| **MLP 的 GEMM + 激活融合** | 官方有 `aclnnFFNV3`（dense FFN 融合），**但 activation 不含 SiTU** | `torch.ops.kimi3_ops.situ_glu_fused` | 替换 MLP 的两段式为一段 | ⚠️ 数值 PASS，**当前负收益**（§2.4 追问预案） |

**一句话**：官方 recipe 覆盖的是「K3 能跑起来」；**我加的是官方没有的那三件** ——
**SiTU 变体的补缺 kernel、dense MLP 的 SiTU 融合（华为 `aclnnFFNV3` 不含这种激活）、LatentMoE 的图接线**。这就是"用我的算子部署"的实质。

### 3.2 装载链路（部署工程视角，5 步）

```bash
① 编 & 装算子（vendor 机制；**多个包会互相覆盖** ⇒ 用三算子合一的 Kimi3Ops 包）
   cd kernels/Kimi3Ops && bash build.sh                     # → dist/*.run
   ./dist/custom_opp_*.run --install-path=$ASCEND_HOME_PATH/opp --quiet
   export ASCEND_CUSTOM_OPP_PATH=$ASCEND_HOME_PATH/opp/vendors/customize
   export LD_LIBRARY_PATH=$ASCEND_CUSTOM_OPP_PATH/op_api/lib:$LD_LIBRARY_PATH

② 在镜像里固化（**这一步是部署与"我本机试过了"的分界线**）
   把上面的 vendor 目录 + 环境变量写进 Dockerfile；基础镜像用官方 `quay.io/ascend/vllm-ascend:kimi-k3-a3`

③ 让框架能调到：`import integration.torch_ops_kimi3`（注册 `torch.ops.kimi3_ops.*`，含 fake/meta、CPU 兜底）
   —— 只有注册了，图捕获与显存预估才有定义

④ 落进模型文件：KIMI3 的 MLP/MoE 处替换 `act_fn`（**SiTU-GLU 是模型私有算子，没有 `CustomOp.forward_npu` 挂载点**，
   接入点必然在模型实现文件里，见 `docs/12` §3）

⑤ 验收：数值（同权重对拍）→ 性能（达标率 / TTFT-TPOT）→ 回归（未替换版本对照）
```

### 3.3 版本配套（**部署方案里最容易踩死的一环**）

| 组件 | 值 | 备注 |
|---|---|---|

### 3.4 收益怎么报（三层账，别跨行相加）

| 层 | 内容 | 数字 | 证据 |
|---|---|---|---|
| ① 补缺 | torch 组合（6 个 elementwise）→ 1 个 kernel | `12d` = 258 KiB/token | ✅ 实测 4.45x~7.68x |
| ② 融合 | 独立算子 → 融进 GEMM epilogue | `4d` = 88 KB/token | ⚠️ 账面；**当前实现是负收益** |
| ③ 融合 | AttnRes 4 算子 → 单 kernel | `8(B+1)H` = 576 KiB/token | ✅ kernel 实测 |
| — | 合计（阶梯，不可相加） | ≈ **920 KiB/token** | `docs/17` §2 |

**并且一定补上**：prefill 4096 token 时每层 ≈3.2 ms（估算）；**decode 可忽略（0.065%）**；
③ 的达标率只有 27.8%，说明这部分"省"未必线性兑现。

### 3.5 验收判据（部署交付时说这几条，专业度立刻不同）

| 项 | 判据 |
|---|---|
| 数值正确性 | 同权重对拍，用 **`±(atol + rtol·|ref|)`**，不用纯相对误差（`|ref|≈0` 处会把 bf16 正常绝对误差放大成假失败） |
| 算子性能 | 访存型算子看**带宽达标率 ≥80%**；算力型看 **MFU ≥70%**；小 shape 换「启动开销 + 搬运」判据 |
| 整层收益 | 官方 `KimiMLP` 同权重前向对比（已做：1.75x） |
| 端到端 | TTFT / TPOT / 吞吐，**对照未替换版本**；PD 分离另算 |
| 回归 | 关掉我的算子（`--enforce-eager` / 回退 native 实现）应回到基线 |

## 4. 一页速答（速查 3 分钟看这段）

**问❌那格**：不做。卡点是 `triton-ascend >= 3.2.1`（公开源最高 3.2.0）+ `vllm-ascend 0.23.0` 要 CANN 9.1.0，
本机 9.0.0 且没有 docker 用官方镜像。**它证明的是"框架装得起来"，不是"算子做得好"**。
框架能不能调到我的算子，我已经用 **`torch.ops` 注册 + fake/meta + `torch.compile` 图捕获**证明了；
再往上还有 **真实模型层**（官方 `KimiMLP` 同权重 **0/131,072**、整层 **1.75x**）。

**问①「比华为提升多少」**：换分母。华为没有 SiTU-GLU/AttnRes ⇒ 分母是等价 torch 组合（**4.45x~7.68x**、达标率 **81.5%**）；
能直测的 KDA 精度差 **4.4e-3**、**无性能优势**；同族 `SwiGlu` **已实测**：大 shape 我慢 **2.31x**
（根因 = 我 **V 计算受限 93.5%** vs 它**访存受限 96%**，不是搬运实现差）；
真正值得比的是**融合深度**：华为有 dense FFN 融合 `aclnnFFNV3`，**但激活不含 SiTU** ⇒ 我补的是这一种激活，
而且**图级对比从此有明确对手**（可与其 swiglu 形态比「融合 vs 不融合」的收益幅度）。
省的是 **HBM 往返**、**只在 prefill 放大**。
**诚实项**：融合算子当前**负收益**（GEMM tiling 只到峰值带宽 4%），要收益先得把 GEMM 做到能和内置打平。

**问②「怎么部署 K3」**：官方镜像 + 官方 recipe 打底（64 卡 / 4 节点 A3、`DP4/TP16/EP64`、
MXFP4 软件反量化、≥8 节点才上 1M 上下文）；**我加三件官方没有的**：
SiTU 补缺 kernel、dense MLP 的 SiTU 融合（`aclnnFFNV3` 不含 SiTU）、LatentMoE 图接线；
装载链路 = 编 `.run` → vendor 目录（多包会互相覆盖 ⇒ 用三算子合一的包）→ 打进镜像 → 模型文件里换 `act_fn`；
验收 = 同权重对拍 + 达标率 + TTFT/TPOT 对照未替换版本。

**系统指标我有数**：自研 mini 引擎（**组件全用真算子**：内置 `npu_fusion_attention` + 官方 `KimiMLP` + 自研 `situ_and_mul`）
跑出 **TTFT 12.17 ms / TPOT 6.60 ms / 2433.7 tok/s**（medium：H=4096、**D=11008**、L=8、权重 3.02 GiB），
并量出 **Amdahl**：单算子能快好几倍，**整机 TPOT 只改善 7.3%** ⇒ **算子优化 ≠ 系统优化**（`docs/14` §19）。
