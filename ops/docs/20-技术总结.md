# 20 - 技术总结：我做了什么 · 比华为如何 · 能不能跑

> 用途：被问到「**你的算子比华为的好在哪**」「**你做了啥**」「**能跑吗**」时，照这个说。
> 三个原则：**定性先立** → **数字全报（含不利的）** → **差距主动先说**。

---

## 0. 一句话定性（必须先说，否则后面全是错的）

> **"我做的不是'比华为更好'，而是'补华为没有的'。"**

华为的 GLU 家族（`SwiGLU`/`GeGLU`/`Glu`/`ClippedSwiglu`）**全是固定激活**，
而 KIMI3 用的 **SiTU 不在其中、也配不出来**；K3 的 **AttnRes 残差栈华为也没有**。
⇒ 我补的是**位置**，不是**水平**。**先立住这句，后面所有数字才站得住。**

---

## 1. 30 秒版（现场）

> 「我做的是**两个华为没有的算子**：**SiTU-GLU** 和 **AttnRes** —— 华为的 GLU 家族全是固定激活
> （sigmoid/silu/gelu），**没有 SiTU**，也配不出来；AttnRes 更是没有。
>
> 都是 **NPU 上的 CANN 算子（AscendC kernel）**，和华为内置算子**同卡、同 shape、同口径**比：
> 相对**等价的 torch 朴素实现**我快 **3.5~7.5x**；但相对**华为同族的 `SwiGLU`**，我**慢 1.7~2.2x** —— 这个我如实报。
> 慢的原因我拆清了：不是搬运差，是 **SiTU 的数学更贵**（3 个超越函数 vs 1 个），用 msprof 和变体实验都验证过，
> 并且我已经把它优化掉了 **13.6%**。」

---

## 2. 90 秒版（展开用）

**① 我做了什么（4 条，分性质说）**

| 项 | 性质 | 状态 |
|---|---|---|
| **SiTU-GLU**（`SituAndMul`） | **补缺**（华为无此激活，且 GLU 家族固定激活配不出） | ✅ 真机对拍 0 超容差、达标率 **89.8%**、已优化 **-13.6%** |
| **AttnRes**（mini-attention 残差栈） | **补缺**（华为没有） | ✅ **0 / 16,777,216 超容差**；27.8%（**结构受限**，非 bug） |
| **LatentMoE 接线** | **独立复现**（官方 recipe 里也有） | ✅ 与官方 `KimiSparseMoeBlock` 同权重 **0 / 384** |
| **GEMM+SiTU 融合**（`SituGluFused`） | **探索（失败）** | ⚠️ 数值 PASS，**但负收益**（812.6 vs 两段式 44.2 µs） |

**② 比华为如何——三个数全报**

| 口径 | 结果 | 说明 |
|---|---|---|
| vs **等价 torch 组合** | **快 3.5~7.5x** | 这是"**没有自定义算子时的真实成本**"，是收益倍数的**唯一正确分母** |
| vs **华为同族 `SwiGLU`** | **慢 1.7~2.2x** | 同卡同 shape 同口径；两条独立路径都测过，**不确定性在对手侧** |
| 整层 MLP（官方 `KimiMLP` 同权重） | **1.69x** | Amdahl：算子级优势会被 GEMM 稀释 |
| 系统 TPOT（自研 mini 引擎） | **1.08x** | **算子优化 ≠ 系统优化**（decode 每步读 3.02 GiB 权重） |

**③ "慢"的原因（有实测，不是解释）**

- msprof：我 `aiv_vec_time` **93.5%**（**计算受限**）vs `SwiGLU` 的 `mte2` **96%**（**访存受限**）
- **变体对照实验**：把 3 个超越函数全去掉 ⇒ 我跑到 **240 µs ≈ 它的 226.7 µs**
  ⇒ **差距 100% 来自数学成本**（SiTU 要 2×tanh + sigmoid + div），不是搬运实现差
- 已优化 **-13.6%**（`E^{−g/2}` 复用：把 2 个超越函数压成 1 个 `Exp`），达标率 **77.6% → 89.8%**

**④ 能跑吗——能，而且不止能跑**

✅ 数值对拍 0 超容差（含 `β≠4` 回退路径）
✅ `torch.ops.kimi3_ops.*` 注册 + fake/meta + `torch.compile` **图捕获**
✅ 接进官方 `KimiMLP`：整层 **1.69x**、超容差 **0/131,072**
✅ 三个算子打进**一个包**（多算子共存）+ 能进 GE 图（`npu_supported_ops.json`）
✅ **两条调用路径**：`torch.ops` / **裸 C++ 直调 `aclrt+aclnn`**（不经 torch）

**⑤ 我差在哪（主动先说）**

| 差距 | 事实 |
|---|---|
| 单算子水平 | 慢 **1.7~2.2x**（数学更贵已拆清，但离极限还有距离） |
| 融合 | **负收益**（根因：自写 GEMM 的 tiling 只到峰值带宽 **4%**） |
| 生态 | 华为 **900+ 算子**、带量化、大规模验证；**我只补了 2 个点** |
| 端到端 | vLLM 装不上（`triton-ascend ≥3.2.1` 公开源拿不到）⇒ 用**自研 mini 引擎**给系统数字 |

> **收尾句**：「**我知道差距在哪，也知道下一步怎么补**」——
> 比"我快 5 倍"值钱得多，因为前者经得起追问。

## 3. 追问预案（最容易被打的 6 个）

| 追问 | 答法 |
|---|---|
| 「**5 倍是不是挑软柿子？**」 | 「分母是**等价 torch 朴素实现**（vLLM 里真就这么写），不是我挑的；**跟华为同族的 `SwiGLU` 比我慢 2x**，这个我也报。」 |
| 「**拿不同函数比有什么意义？**」 | 「**不比分母**（分母必须功能等价）；**只比参照**（同族最强）。比的是**时间/带宽**，不是"谁算得对"—— 我实测两者 `max_rel = 4.54`，差 454%，本来就不是一个函数。」 |
| 「**那这不就是 SwiGLU 吗？**」 | 「**SwiGLU 的"Si"来自 Swish，SiTU 的"Si"来自 Sigmoid** —— 前缀撞车。SwiGLU 是 `silu(gate)·up`（up 直通）；SiTU 两个分支都被压缩（3 个超越函数）。」 |
| 「**华为没有，所以你没对手，随便吹？**」 | 「**没有同规格 ≠ 没有参照**：分母管"值不值得"（3.5~7.5x），参照管"水平如何"（慢 2x）—— 两件事都答。」 |
| 「**为什么没接 vLLM？**」 | 「卡在 `triton-ascend ≥3.2.1`（公开源最高 3.2.0，且 3.2.0 与 CANN 9.0 不配套、跑不了 kernel）—— **外部依赖，不是算子问题**。我用自研 mini 引擎给系统数字补上了这一段。」 |
| 「**融合怎么是负收益？**」 | 「**能跑对 ≠ 有收益**。融合的收益上界只有几十 µs（省 88 KB/token ÷ 带宽），而自写 GEMM 慢了 770 µs。**要收益，前提是先写出能和内置 `MatMul` 打平的 GEMM** —— 我先补这个。」 |

---

## 4. 三条不能说的话（会当场掉分）

1. ❌ 「**我比华为快 5 倍**」 —— 分母不对（那是 torch 组合，不是华为算子）。
2. ❌ 「**华为没有 SiTU，所以我的更好**」 —— 补缺 ≠ 更强；要同时报"离同族最好还差 2x"。
3. ❌ 「**我的融合省了 88 KB/token**」 —— 那是**账面**；实测是**负收益**，说账面会被追问当场打脸。
