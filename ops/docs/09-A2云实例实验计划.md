# A2 云实例实验计划（登上去之后按这个走）

> 背景：当前这个容器（A3 切片）卡住了三件事——**没有 RoCE 网卡**、**只有 1 个节点**、
> **没有执行权限**。A2 云实例能登录 + 有 root，很可能把这三条都解开。
>
> 原则：**先探测再投入**。5 分钟就能知道这台实例到底能做什么，别先动手改代码。

---

## 1. 为什么 A2 实例比当前容器强

| 维度 | 当前 A3 容器（切片） | A2 云实例（预期） |
|---|---|---|
| 登录/权限 | 容器，`bash` 被拒 | **云主机，你有 root** |
| NPU 卡数 | 2 张（借的 davinci4/5） | 通常 8 张（Atlas 800 A2） |
| **RoCE 网卡** | ❌ 宿主都没启用 | ✅ **智算实例通常标配** |
| 节点数 | 1 | 你能开几台？（同 VPC 才有内网互通） |
| CANN | 9.0.0（A3 定制包） | 可能是 8.x，**先确认版本** |
| SOC | `ascend910_93` | **`ascend910b`** ← 算子要改 |

## 2. 第一步：探测（5 分钟，先跑这个再决定做什么）

仓库里已经有现成脚本，`scp` 或直接粘贴过去跑：


两条脚本会打印全部原始输出，并在末尾给"走哪条路"的结论。**手动最小版**：

```bash

ibv_devices                                     # ★ RDMA 设备有没有
ibv_devinfo | grep -E "hca_id|link_layer|state|rate"

lspci -nn | grep -i -E "mellanox|huawei"        # 网卡硬件
cat /usr/local/Ascend/driver/version.info       # 驱动版本
ls /usr/local/Ascend/                           # CANN 版本（注意可能不是 9.0.0）
python3 -c "import torch, torch_npu; print(torch.npu.device_count())"
```

## 3. 按探测结果分流

### 情况 A：`ibv_devices` 列出了设备（大概率）

**这台机器能直接做目前最缺的那条线**：

```bash
# 真实带宽/延迟（当前容器完全拿不到的数字）
ib_write_bw -d <dev> -g <gid>                    # 终端1（server）
ib_write_bw -d <dev> -g <gid> <对端IP>            # 终端2（client）
ib_send_lat -d <dev> -g <gid>

# verbs 编程模型（我写好的最小程序）
cd rdma_host_demo && make && ./rdma_verbs_demo <dev> <gid>
```

### 情况 B：没有 `ibv_devices`，但你有 root

→ **SoftRoCE**（普通以太网卡即可）：

```bash
sudo apt install rdma-core libibverbs-utils librdmacm-utils perftest
sudo modprobe rdma_rxe
sudo rdma link add rxe0 type rxe netdev eth0
ibv_devices                                      # 应看到 rxe0
```

能验证编程模型；**带宽数字无意义**（软件栈），这一点必须自己先说。

### 情况 C：连 root 都受限

→ 退到"只读探测 + 文档"，别硬来。

## 5. ⚠️ A2 与 A3 的差异清单（算子迁移必看）

把本项目的算子搬去 A2 要改的地方，**一共两处**：

```cpp
// op_host/*.cpp
this->AICore().AddConfig("ascend910_93");   →   this->AICore().AddConfig("ascend910b");
```

```json
// kernels/*/CMakePresets.json
"value": "ascend910_93"                     →   "ascend910b"
```

**kernel 本体不用动**——因为 `tileElem` 已经是 host 端按 UB 容量反推、`blockDim` 查 AIV 核数，
换 SOC 会自动跟着变。这正是前几轮那次改造的收益。

其余要确认的：

| 项 | 为什么 |
|---|---|
| CANN 版本 | 云实例可能是 8.x，`platform_ascendc` 头文件路径/API 可能有差异 |
| torch_npu 版本 | 必须与 CANN 配套 |
| 驱动版本 | 决定 HCCL 可用特性（如 `HCCL_INTRA_ROCE_ENABLE` 是 A2 专用开关） |
| 具体 SOC 子型号 | `ascend910b` 还有 b1/b2/b3/b4，`npu-smi` 的 Name 列能看出 |
| 多机时 | `HCCL_SOCKET_IFNAME` 必须指定 RoCE 网卡 |

## 6. 最关键的一句

**A2 实例上最该做的不是 RDMA，是把算子的"未验证"状态消掉。**

> ★ **2026-09-19 更正**：这个前提在 A3 容器上**已经不成立** —— `SituAndMul` / `AttnRes` 已在真机上编译、
> 对拍并量到达标率（`docs/14` §2、§9、§10），`SituGluFused` 重建版也已上机对拍 PASS（§16.4）。
> 本节余下内容作为「换到 A2 实例后按什么顺序做」的操作清单仍然有效。

当前仓库里我改过/写过的代码（kernel、bench 脚本、hccn 脚本）**换机器后仍需重跑一遍**，
这是最大的风险项。A2 上只要：

```bash
source /usr/local/Ascend/<cann版本>/set_env.sh
cd kimi3_ops/kernels/SituAndMul && bash build.sh          # 先编译
cd ../.. && python test_situ_real.py                       # 再对拍
python bench_situ_real.py --bench-bw-only                  # 再出达标率
```

这三步跑通，"作品集里有未验证代码"这个坑就填上了——**比多发一篇文档有价值得多**。
