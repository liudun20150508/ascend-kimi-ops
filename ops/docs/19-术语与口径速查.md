## 1. tiling（分块）

**定义**：因为**片上内存装不下整个张量**，把任务切成小块，并决定"**每块多大、怎么分给多个核**"。

**本项目怎么用**（两级落地）：

```
host 侧算参数  →  写进 tiling 结构体  →  kernel 侧按它循环
```

```c
struct SituAndMulTilingData {
    uint32_t d, numRows;                     // 形状
    uint32_t blockDim;                       // 用多少核（host 查 AIV 核数）
    uint32_t tileElem;                       // ★ 每块多少元素（核心参数）
    uint32_t tilesPerRow, totalTiles;        // 怎么分
    float beta, linear_beta, invBeta, invLinearBeta;   // 常量也放这里
};
```

**关键：`tileElem` 是从 UB 容量反推的，不是调参试出来的**：

```
UB 每元素占用预算：
  输入 gate 队列 depth=2 × bf16 = 4 B/元素
  输入 up   队列 depth=2 × bf16 = 4 B/元素
  输出 out  队列 depth=2 × bf16 = 4 B/元素
  片内 fp32 计算缓冲 3 块 × 4B  = 12 B/元素
  ──────────────────────────────────────
  合计 = 24 B/元素
tileElem = UB × 0.5 / 24 → 向下对齐 256 元素
```

**多核怎么分**：按 **tile** 均分（`tilesPerCore = ceil(totalTiles / blockDim)`），**不是按整行** ——
`d` 不是核数整数倍时按行分会尾核空转，长尾从"一行"缩到"一个 tile"。

**GEMM 的 tiling 是另一套（三级）**：`L0C → L0A/L0B → L1` 反推，见 `docs/05`。

出处：`kernels/SituAndMul/op_kernel/situ_and_mul_tiling.h`、`op_host/situ_and_mul.cpp`、`docs/04` §3、`docs/05`。

## 2. baseline / 基线（**四种用法，别混**）

**核心原则**：**baseline 不是固定对象，而是"回答某个问题时选定的对照物"。**

| # | 是什么 | 回答哪个问题 | 结果 |
|---|---|---|---|
| ① | **串行版 kernel**（去掉 double buffer） | double buffer 有没有收益？ | ❌ 没有（0.4003 vs 0.4005 ms） |
| ② | **原版 kernel**（优化前：2×Tanh+1×Sigmoid） | 变体优化收益多少？ | ✅ 457 → 395 µs（-13.6%） |
| ③ | **等价 torch 组合**（6 个 elementwise） | **收益倍数**是多少？ | ✅ 3.5~7.5x |
| ④ | **两段式（不融合）** | **融合有没有收益**？ | ❌ 负收益（812.6 vs 44.2 µs） |

**唯一固定的是 ③**：它是**收益倍数的分母**，永远是「**等价功能的朴素实现**」，**不能换成华为算子**（口径 A）。
出处：`docs/04` §10。

## 3. 融合（只有一个硬定义）

**定义**：**让中间张量不落 HBM。**

| 粒度 | 例子 | 省什么 |
|---|---|---|
| **elementwise 合并**（6 个 torch 算子 → 1 kernel） | `SituAndMul` | `12d`/token |
| **GEMM + 激活**（epilogue 融合） | `SituGluFused` | `4d`/token |
| **整层 MLP** | 华为 `FFN`（`aclnnFFNV3`） | `6d`/token |

❌ **不算融合**：vLLM 的 `merged gate_up_proj` —— 只是**权重拼接**（输出照样落 HBM），只少一次 launch。
出处：`docs/17` §1.2/§1.4。

**★ 每个算子"各自的对手"（这个最容易被问混）**：

| 我的算子 | 粒度 | 输入 → 输出 | 华为对应物 | 状态 |
|---|---|---|---|---|
| **`SituAndMul`** | 单算子 | `[M,2d] → [M,d]` | **`SwiGlu`**（`aclnnSwiGlu`，同形态、同搬运量） | ✅ 已比：**慢 1.7~2.2x** |
| **`SituGluFused`** | GEMM + 激活 | `x[M,K] + W → y[M,d]` | `FFN`（整层 MLP） | ⚠️ 粒度仍不同 ＋ 本机**建图失败** |
| `SituGluFused` 的**直接对照** | —— | —— | **我自己的两段式**（`Matmul` + `SituAndMul`） | ✅ 已测：**负收益** |

- **跟 `SwiGlu` 比的是 `SituAndMul`，不是 `SituGluFused`** —— 因为 `SwiGlu` 不含 GEMM，粒度必须对齐。
- `SituAndMul` 自己**已经是"elementwise 级融合"**（6 个 torch 算子 → 1 kernel），
  但两边都不含 GEMM ⇒ 对比时**"融合"不是变量**，变量只有"**激活函数的计算量**"（我 3 个超越函数 vs 它 1 个）。

## 4. 坐标系（谁的数、在哪算）

| 角色 | 在哪算 | dtype |
|---|---|---|
| ① 等价 torch 组合（**性能分母**） | **NPU** | bf16 |
| ② 自研算子（被测） | **NPU** | bf16 |
| ③ 华为内置算子（对测） | **NPU** | bf16 |
| ④ 精度 golden（`reference/situ.py`） | **CPU** | bf16 |

```
你的代码 → torch 本体(+cpu wheel 只是名字) → torch_npu 插件派发 → aclnn(CANN 层) → AscendC kernel → NPU AI Core
```

**三个高频误解的纠正**：
- "我开发的是 NPU 的 torch 算子" → 🟡 跑在 NPU 对，但它是 **CANN 算子**，torch 只是入口
- "精度比的是 CPU 的 torch" → ✅ 对，**故意**的（正交参考，否则发现不了共同的错）
- "华为的是 NPU 的 torch" → 🟡 华为的算子也是 **CANN 算子**；`torch_npu` 是**另一个东西**（适配插件）

出处：`docs/17` §2.5。

**公平比较的三个条件（缺一不可）**：

| 条件 | 本项目怎么做 | 排除什么 |
|---|---|---|
| **同卡** | 都在 `device 0`（同一张 `Ascend910_9382` 的**同一个 die**） | 硬件 / 频率 / 温度差异 |
| **同 shape** | 都是 `[4096, 22016]`（`d=11008`，K3 真实值） | 规模差异（小 shape 可能强弱反转） |
| **同口径** | **同路径内比**（torch 对 torch、C++ 对 C++） | 测量方法差异（**实测跨路径差 15~26%**） |

⇒ **性能对比全程在 NPU 上**（两边都要落在 NPU，因为要量 NPU 的执行时间）；
**只有"精度 golden"在 CPU** —— 那是刻意的（正交参考）。

**★ 两个高频追问**：

**①「等价 torch 组合」是什么？** —— 用基本算子拼出的、**功能完全等价**的实现：

```python
def torch_reference(x, beta, linear_beta):
    gate, up = x.chunk(2, dim=-1)
    situ = beta * torch.tanh(gate/beta) * torch.sigmoid(gate)
    return situ * (linear_beta * torch.tanh(up/linear_beta))
```

- 它是**分母**（不是对手）：**没有自定义算子时，框架真实要付的成本**（vLLM 里就是这么写的）。
- 它为什么慢：**9 个算子 ⇒ 8 个中间张量落 HBM**，每次"写+读"⇒ 收益来自**少搬**，不是算得快。
- ❌ **不能换成华为算子当分母**（华为没有 SiTU ⇒ 假命题）。

**② `torch.ops` 是 NPU 的吗？** —— **不是**，它是 PyTorch 的**算子注册机制**，**设备无关**：

| 输入 | 输出 device | 走的实现 |
|---|---|---|
| NPU 张量 | `npu:0` | 自研 **AscendC kernel** |
| CPU 张量 | `cpu` | 注册的 **CPU 兜底**（= `reference/situ.py`） |
| fake 张量 | —— | **不碰设备**推出 shape（图捕获需要） |

⇒ **同一个算子名，按张量派发**。所以要注册**三份**：`fake/meta`（图捕获/动态 shape/显存预估）、`NPU`（本体）、`CPU`（退路）。

## 5. 口径 A / 口径 B

- **口径 A**：分母必须是「**等价功能的朴素实现**」，**不能是华为的算子** ——
  SiTU-GLU 华为没有 ⇒ 拿它当分母是**假命题**。
- **口径 B**：省的是 **HBM 往返，不是时间**（换算要除带宽）；而且**只对 prefill 放大**
  （decode 每步读整层权重 ≈1.38 GB，省的 920 KiB 占 **0.065%**）。

出处：`docs/17` §0。

## 6. 达标率 / MFU / 判据的适用域

| 判据 | 适用域 | 出处 |
|---|---|---|
| **带宽达标率 ≥ 80%** | **只对访存受限的算子**（SiTU-GLU 是**计算受限** ⇒ 不适用） | `docs/04` §1（含更正） |
| **MFU ≥ 70%** | 算力受限的算子 | `docs/04` |
| 「启动开销 + 搬运」 | 小 shape（被 15~20 µs 启动开销主导） | `docs/04` §2 |
| **达标率 > 100% ⇒ 判据有 bug** | copy 峰值是 1:1 读写；读多写少的算子会超 | `docs/17` §5 |

**★ 三个算子、三种瓶颈、三种判据（这条是"判据跟瓶颈走"最硬的证据）**：

| 算子 | 瓶颈性质 | 该用什么判据 | 数字 |
|---|---|---|---|
| 华为内置 `SwiGlu` | **访存受限**（`mte2` 93.6%） | 带宽达标率 ≥80% | ✅ 93.1% |
| 自研 `SituAndMul` | **计算受限**（`aiv_vec` 93.5%） | V 吞吐（**带宽口径不适用**） | 89.8%（带宽口径，仅参考） |
| 自研 `AttnRes` | **结构受限**（两趟读 v + ReduceSum 归约） | **跟自己的理论上限比** | 27.8%（**不是 bug**） |

- `AttnRes` 是 K3 的 **mini-attention**（B+1 个残差向量：RMS-norm → score 点积 → softmax → 加权和），
  **华为也没有** ⇒ 同样是**补缺**（分母 = 等价 torch 组合），收益 `8(B+1)H` = **576 KiB/token**（比 SiTU-GLU 的 258 KiB 更大）。
- 它的优化难点是 **UB 容量硬约束**：`H=4096, B=16` 时单 token 需 **557 KB** ≫ 单核 UB（192 KB）
  ⇒ 想把 v 缓存一趟做完**放不下**，只能分块或复读。
出处：`reference/attn_res.py`、`docs/04` §7、`docs/14` §10。

## 13. 「图级」其实是三块（别当成一件事）

| 图级的项 | 是什么 | 对手 | 实测状态 |
|---|---|---|---|
| **① 图级融合** | `GEMM + SiTU` 融进一个 kernel（epilogue 融合）=`SituGluFused` | 华为 **`FFN`**（`aclnnFFNV3`，整层 MLP，**不含 SiTU**） | ⚠️ 数值 PASS，**但负收益**；对手侧建图失败 ⇒ **未测** |
| **② 图接线** | LatentMoE 的 down/up 投影（模型结构适配）=`latent_moe.py` | 官方 recipe（官方镜像里也有） | ✅ 独立复现：与官方 `KimiSparseMoeBlock` 同权重 **0 / 384** |
| **③ 图捕获** | 算子进计算图（ACL Graph / `torch.compile`） | 框架原生 | ✅ `torch.ops` + fake/meta + `aot_eager` 与 eager **差 0.0** |

**① 融合——唯一还没拿到正收益的一块**：

| | 耗时 |
|---|---|
| 自研融合 `SituGluFused` | **812.6 µs** |
| 内置 `MatMulV2` 单算子 | 39.88 µs ⇒ 我慢 **20.4x** |
| 两段式（`Matmul` + `SituAndMul`） | **44.2 µs** ⇒ 融合**比不融合还慢 18x** |

根因：**自写 GEMM 的 tiling 只跑到峰值带宽 4%**。

**图级最大的教训**：**融合的收益上界 = 省的字节 ÷ 带宽**（`88 KB/token` ⇒ 折算只有几十 µs），
**而代价（自写 GEMM 慢 770 µs）远大于它** ⇒ **要拿融合收益，前提是先写出能和内置 `MatMul` 打平的 GEMM**。

**② 接线的三条不变量**：`gate` 用**投影前** hidden / experts 工作在 **latent 维** / `shared_experts` 走**原始 hidden**。

## 9. Triton（vs AscendC vs torch 组合）

**定义**：Triton 是**面向加速器的 kernel 编程语言 + 编译器**（OpenAI 开源，Python 内嵌 DSL，`@triton.jit`）。
你只写**块级（tile）**操作（`tl.program_id` / `tl.arange` / `tl.load` / `tl.store`），
**编译器负责**内存分配、数据搬运、流水并行、向量化 ⇒ **比 CUDA / AscendC 高一层抽象**。

**昇腾上的 Triton = `triton-ascend`**（华为官方移植：`gitcode.com/Ascend/triton-ascend`），
也是 **`vllm-ascend` 的硬依赖**（0.23.0 要求 `triton-ascend==3.2.2`）。

**三者的抽象层次与代价**（本项目**同一个算子** SiTU-GLU 的实测）：

| | 代码量 | 谁做 tiling / 流水 | 性能上限 | 可移植性 |
|---|---|---|---|---|
| torch 算子组合（6 个 elementwise） | 3 行 | 框架 | 最低 | 最好 |
| **Triton**（`triton_kernels/situ_glu_triton.py`） | **kernel 本体 ~22 行** | **编译器** | 中高 | 好（换后端重编） |
| **AscendC**（`kernels/SituAndMul/`） | **kernel 193 行 + host 137 行** | **人**（`TQue`/双缓冲/tiling 全手写） | **最高** | 差（换芯片重写） |

**本机实测状态**：`triton-ascend 3.2.0` 已装、`import` 通，
但**跑 kernel 时 driver 初始化编 `npu_utils.cpp` 失败**（`RT_LIMIT_TYPE_SIMT_WARP_STACK_SIZE` 不在 CANN 9.0 驱动头里）
⇒ **本机跑不了** ⇒ 三实现对比目前是 **2/3 有数据**（CANN 内置 + AscendC 有数，Triton 缺）。

**为什么这条线值得留**：它证明"**我知道什么时候用哪种工具**" ——
Triton 换来**开发效率与可移植性**，AscendC 换来**性能上限**（能手写双缓冲/tiling）。
出处：`docs/06`、`triton_kernels/situ_glu_triton.py` 头部。

## 10. 对拍（duì pāi）

**定义（芯片/算子圈行话）**：把**被测实现**的输出与**标准答案（golden / 参考实现）**逐元素比对，
看误差是否落在容差内 —— 即"**拿两个独立实现跑同一组输入，比结果**"。

**本项目一次对拍的全流程**（`test_situ_real.py`）：

```python
torch.manual_seed(seed)                                    # ① 固定 seed ⇒ 可复现
x = (torch.randn(shape, dtype=torch.bfloat16) * 6.0).npu()  # ② 输入在 NPU；×6 覆盖 tanh/sigmoid 饱和区
ref = situ_golden(x.cpu(), beta, linear_beta)               # ③ golden：CPU 上的纯 torch 参考实现
out = run_real(x, beta, linear_beta)                        # ④ 被测：自研 AscendC 算子在 NPU
err = (out.cpu().float() - ref.float()).abs()
rel = (err / (ref.float().abs() + 1e-3)).max()               # ⑤ 相对误差（+1e-3 防除零）
assert out.shape == ref.shape and out.dtype == ref.dtype     # ⑥ shape / dtype 也要比
# 判定：rel < 1e-2 → OK
```

**四个关键决策（问答必被追问）**：

| 决策 | 为什么 |
|---|---|
| golden 在 **CPU**、被测在 **NPU** | **正交参考** —— 两条路径独立，才**发现得了共同的错**（共用一套实现 = 自证） |
| 判据用 `±(atol + rtol·\|ref\|)` 而非纯相对误差 | `\|ref\|≈0` 处会把 bf16 的正常绝对误差放大成**假失败**（实测：改判据前 6 个算子全 FAIL） |
| 容差取 **1e-2** | bf16 只有 8 位尾数，这是格式决定的量级（实测 max_rel 7~9e-3，留有余量） |
| **固定 seed** | 可复现：换机器/重跑，输入完全一样，数字可比 |

**对拍的三个层次**：单元（单算子）/ 集成（真实模型层 `l2_mlp_check.py`）/ 替换等价（vs 框架原生）。

**对拍的反面：负对照**（`scripts/negative_control.py`）——
**"对拍通过" ≠ "算子是对的"**，也可能是判据太松 ⇒ 故意用错参数，对拍**必须报警**。

**官方工具**：CANN 自带 `tools/operator_cmp/compare`（算子精度对比）。

**别和对 bench 混**：对拍 = **正确性**，bench = **性能**；顺序必须**先对拍、后测性能**。

## 11. 「LatentMoE 接线」≠「vllm-ascend 装不上」（别串成因果）

这两件事**经常被串成因果，但毫无关系**：

| | **LatentMoE 图接线** | **vllm-ascend 加载不了** |
|---|---|---|
| 问题性质 | **模型结构**问题 | **环境依赖**问题 |
| 卡在哪 | 框架的 MoE 类（vLLM `FusedMoE`）假设输入是 **hidden 维**，而 K3 的 MoE 工作在 **latent 维（3584）** | `triton-ascend >= 3.2.1` **公开源拿不到** |
| 怎么解决 | 框架 MoE 前后**加 down/up 投影 + norm**（接线，**不用新 kernel**） | 等包发布 / 官方镜像（要 CANN 9.1.0） |
| 做完之后 | ✅ 证明"能在框架里正确接 K3 的 MoE"（0/384） | ❌ **不会**因此装得上 |

**三条必须记住的**：

1. **两者独立**：接线做完不会让 pip 装得上；装上 pip 也仍然需要接线。
2. **官方 recipe 里也有这一步**（否则官方镜像跑不了 K3）⇒ 我做的是**独立复现 + 验证**，
   **不是**"没我的接线就跑不起来"。
3. **能不能加载 vllm-ascend，只取决于 `triton-ascend >= 3.2.1`**（或 CANN 9.1.0 + 官方镜像）。

**LatentMoE 接线的三条不变量**（最容易写错，`integration/latent_moe.py` 的自检专盯这三条）：

1. `gate` 用**投影前**的 hidden（H 维）算 topk，不是 latent 空间；
2. experts 的 `hidden_size = moe_hidden_size`（**latent 维**），不是 H；
3. `shared_experts` 走**原始 hidden**，不经过 down/up 投影。

出处：`integration/latent_moe.py`、`docs/12` §4、`docs/18` §3.1。

## 12. `SwiGLU` ≠ `SiTU`（名字撞前缀，函数完全不同）

**这个混淆很致命**：如果 `npu_swiglu` 就是 SiTU，那我"补缺"的整个论证就塌了。**实测证明不是**。

| | 全称 | **"Si" 来自** | 公式 |
|---|---|---|---|
| **SwiGLU** | **Swi**sh-Gated Linear Unit | **Swi**sh（= SiLU） | `silu(gate)·up` |
| **SiTU** | **Si**gmoid + **T**anh Unit | **Si**gmoid | `β·tanh(g/β)·σ(g) · lb·tanh(up/lb)` |

**结构差异（本质）**：

| | gate 分支 | up 分支 | 超越函数个数 |
|---|---|---|---|
| **SwiGLU** | `silu(gate) = gate·σ(gate)` | **直通** | **1 个**（sigmoid） |
| **SiTU** | `β·tanh(g/β)·σ(g)` | `lb·tanh(up/lb)` | **3 个**（2 tanh + sigmoid + div） |

⇒ **SiTU 两个分支都被压缩，SwiGLU 只门控 gate、up 直通** —— 结构性差异，不是参数差异。

**实测（同一输入，`torch_npu.npu_swiglu` vs `aclnn_ops.situ_and_mul`）**：

```
max|diff|   = 245.0000
max_rel     = 4.5414      ← 454%
中位相对差   = 0.2933      ← 中位数就差 29%
```

⇒ **拿 SwiGLU 当 SiTU 用，误差几十个百分点** ⇒ 不可替代 ⇒ **补缺成立**。

> **对方很可能就问"这不就是 SwiGLU 吗"** —— 准备好这个 **454%** 的实测数字，比背公式强。
> 这也解释了为什么"拿 SwiGLU 比只能比时间/带宽，不能比谁算得对"：**它们算的根本不是同一个东西**。

### 12.1 追问「那它不就是 GLU 吗？」—— 是，但要看哪一层

| 层次 | 定义 | 例子 |
|---|---|---|
| **最泛（广义 GLU）** | 两分支逐元素相乘（gated） | **SiTU**、SwiGLU、GeGLU、GLU |
| **标准 GLU** | `a ⊗ σ(b)`（b 过 sigmoid，a 直通） | `aclnnGlu` |
| **GLU 变体（换激活）** | `act(a) ⊗ b` | SwiGLU(silu)、GeGLU(gelu)、ReGLU(relu)、ClippedSwiglu |
| **SiTU** | `β·tanh(g/β)·σ(g)` ⊗ `lb·tanh(u/lb)` | ← 两分支**都变换**，gate 是 `tanh×sigmoid` 乘积 |

**⇒ 广义层：是 GLU ✓；变体层：不在华为提供的那组激活里 ✗**（CANNN 的 GLU 家族**全是固定激活**，接口无激活参数）。

**能"拼"出来 ≠ 有对应算子**：理论上 SiTU 可用 `Glu(β·tanh(g/β), g)` + `lb·tanh(u/lb)` 拼出来，
但那要 **5~6 个算子 + 中间张量** —— 而这**正是 `SituAndMul` 要替代的东西**（6 个 → 1 个 kernel）。

⇒ **"补缺"的两层含义**：① 算子层没有 SiTU 这个激活；② 把它从"5~6 个算子的拼法"变成"1 个 kernel"。
