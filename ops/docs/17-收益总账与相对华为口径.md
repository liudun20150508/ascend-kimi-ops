# 17 - 收益总账与「相对华为」的正确口径

> 触发场景：追问里被问「**你的提升是多少**」「**相对华为快多少**」。
> 这份文档把散在 `docs/03`、`docs/04`、`docs/11`、`docs/14` 与 `../benefit_total.py` 里的收益证据收成一本账，
> 并且给每个数字标上**证据等级**（实测 / 可推 / 账面）。

**★ 先说结论（三句话，别答错）**

1. 「相对华为的提升」对 **SiTU-GLU / AttnRes 是假命题** —— 华为没有这两个算子（GLU 家族里没有 SiTU 变体）。
   能给的是**补缺**，分母必须是「等价的 torch 朴素实现」。
2. 能跟华为**直接对测**的只有 **KDA**（`aclnnChunkKdaFwd`）：精度对齐 ~4.4e-3，**没有性能优势可吹**。
3. 真正值得比的是**融合深度**：华为在 MoE 的 GMM 场景做了 `GroupedMatmulSwigluQuant`，
   而 **dense MLP 的 FFN 融合华为其实有**（`aclnnFFNV3`：`y=act(xW1+b1)W2+b2`，无专家形态即 dense MLP），
   **但它的 `activation` 只支持 fastgelu/gelu/relu/silu/geglu/swiglu/reglu —— 不含 SiTU**；
   我补的正是**这一种激活**，省的仍是中间张量的 HBM 往返。

### 口径 A：基准必须是「等价功能的朴素实现」，不是「华为的算子」

```python

```

## 1. 相对华为：三种关系（附证据强度）

| 关系 | 对象 | 证据 | 强度 |
|---|---|---|---|
| **补缺** | SiTU-GLU、AttnRes | `README.md` 缺口清单：`SiTU-GLU ❌ 只有 SiLU`、`AttnRes ❌ 无` | ★★★ 仓库内两处独立记载（`kimi3_ops/README.md` §缺口清单、本文件） |
| **同类可比** | KDA | `docs/03`：与 `aclnnChunkKdaFwd` 对拍，attn_out/final_state ~4.4e-3（4 个 case） | ★★★ 真机对拍 |
| **华为也在做同类融合** | `GroupedMatmulSwigluQuant`/`V2`（MoE GMM）＋ **`FFN`/`aclnnFFNV3`（dense FFN：`y=act(xW1+b1)W2+b2`）** | CANN 910_93 算子清单 **＋ 本机头文件** `aclnn_ffn_v3.h`（能直接读到 `activation` 支持列表） | ★★★ **头文件直读**（强证据） |

### 1.1 华为的 GLU 家族有哪些（CANN 910_93 内置算子清单，本机可复查）

清单目录：`/usr/local/Ascend/cann-9.0.0/opp/built-in/op_impl/ai_core/tbe/config/ascend910_93/`

```
aic-ascend910_93-ops-info-{cv,legacy,math,nn,oam,transformer}.json
```

在 `...-ops-info-nn.json` 里检索到的 GLU 家族成员：

| 算子 | 行号 | 说明 |
|---|---|---|
| `ClippedSwiglu` | 3173 | 带 clip 的 SwiGLU |
| `DequantSwigluQuant` | 4452 | 反量化 + SwiGLU + 量化 |
| `GeGluV2` / `GeGluGradV2` | 9965 / 9884 | GEGLU |
| `Glu` | 10445 | 通用 GLU |
| `GroupNormSilu` / `GroupNormSiluQuant` | 10622 / 10722 | norm + SiLU（量化） |
| `SwiGlu` / `SwiGluGrad` / `SwiGluQuant` | 15038 / 15093 / 15158 | SwiGLU 激活（含反向、量化） |

在 `...-ops-info-transformer.json` 里：

| 算子 | 行号 | 说明 |
|---|---|---|
| `GroupedMatmulSwigluQuant` | 4932 | **GMM + SwiGLU 融合 + 量化**（MoE 场景） |
| `GroupedMatmulSwigluQuantV2` | 5035 | 同上的 V2 |

**读法（重要，别说过头）**：

- ✅ 可以说：**华为的 GLU 家族里有 `SwiGlu` 等一整套，但没有 SiTU 变体**；
  激活数学不同（SwiGLU 是 `silu(gate)·up`，SiTU 是 `β·tanh(g/β)·σ(g)`），所以我的算子不是"重复造一个已有的"。
- ⚠️ 不能说：「清单里没有就证明华为绝对没有」—— 这些 JSON 是**分类清单**，不是全量枚举
  （反例：我在 `transformer` 分类里检索 `Kda|ChunkKda` 是 **no matches**，
  但 `docs/03` 明确记录了 `aclnnChunkKdaFwd` 的存在与对拍结果）。
  ⇒ **清单检索是弱证据，"仓库内的真机对拍"才是强证据。**
- ★ 真正的价值点：`GroupedMatmulSwigluQuant` 说明「**GEMM + GLU 融合**」是华为自己也在做的方向，
  只是做在 **MoE 的 GMM 场景**；dense 侧华为也有 `aclnnFFNV3`，**但激活不含 SiTU**
  ⇒ 真正的边界是「**激活变体**」，不是「有没有融合」，
  而 vLLM/SGLang 里本来就有 `merged gate_up_proj` 形态 ⇒ 我的融合算子在框架里**有位置**，不是自造。

### 1.2 ★★★ 2026-09-19 新证据（头文件直读）：华为有 dense FFN 融合算子 `aclnnFFNV3`

```c
// /usr/local/Ascend/cann-9.0.0/aarch64-linux/include/aclnnop/level2/aclnn_ffn_v3.h
// 功能描述：该FFN算子提供 MoeFFN 和 FFN 的计算功能
// 计算公式：y = activation(xW1 + b1)W2 + b2
// activation：必选参数…当前支持 fastgelu/gelu/relu/silu 以及 geglu/swiglu/reglu
// weight1/2 支持 [E,K,N]（有专家）或 [K,N]（无专家）⇒ 无专家形态就是 dense MLP
```

**三条结论（这才是"图级能不能比"的答案）**：

| # | 结论 |
|---|---|
| 1 | **华为有 dense MLP 的融合体**（`FFN` 的无专家形态）⇒ **不能说"华为没有 dense MLP 融合"**（旧表述已按此更正） |
| 2 | **但它的 `activation` 清单里没有 SiTU**（只有 fastgelu/gelu/relu/silu/geglu/swiglu/reglu）⇒ 我的边界是「**激活变体**」，不是「有没有融合」 |
| 3 | **图级因此有了明确对手** ⇒ 可以和它比三件事：① **功能覆盖**（SiTU 有没有）② **融合质量**（各自"融合 vs 不融合"的收益幅度）③ **绝对性能**（同 shape） |

> 本机还能直接读到它的 AscendC 源码：`.../op_impl/ai_core/tbe/impl/ops_transformer/ascendc/ffn/ffn.cpp`，
> 以及同族的 `attention_to_ffn` / `ffn_worker_batching` / `ffn_worker_scheduler`
> （这一族是 **MoE 大 EP 的 FFN 调度**，对应 K3 的 896 专家场景）
> ⇒ **设计层面的对比也有材料**，不只是接口层面的对比。

**⚠️ 这条顺带教了一课**："华为 dense MLP 无融合"这个判断原本来自**分类 JSON 的清单检索**，
而 `FFN` 这个名字**看不出它是 FFN 融合**（不带 `Matmul`/`Glu` 字样）——
**"清单里没有"≠"不存在"**；这就是为什么口径要改成"激活变体"，也是为什么证据要升级到头文件直读。

### 1.3 「图级收益对比」能做到哪一步（实测尝试的结论）

探针脚本：`scripts/bench_ffn_aclnn.cpp`（直调 `aclnnFFNV3` vs `matmul+swiglu+matmul` 三段）。
四层对比的可达性，**分清"能比"和"本机能测"**：

| 层次 | 能不能比 | 本机状态 |
|---|---|---|
| ① **功能覆盖**（谁支持 SiTU） | ✅ 能 | ✅ **头文件直读已证**：`FFN` 支持 fastgelu/gelu/relu/silu/geglu/swiglu/reglu，**不含 SiTU** |
| ② **账面收益幅度**（省多少 HBM 往返） | ✅ 能（公式可复算） | ✅ 已算：华为**整层**融合省 `6d`/token；我的**半个 MLP**（gate_up+SiTU）省 `4d`/token |
| ③ **实测收益幅度**（融合 vs 不融合的时延差） | ⚠️ 设计上能 | ❌ **本机做不了** —— 见下 |
| ④ **我自己的融合收益** | ✅ 能 | ✅ 已测：**负收益**（`docs/14` §16：812.6 μs vs 两段式 44.2 µs） |

**③ 为什么本机没测成（实测记录，含一次自我纠错）**：

```bash
# 1) 链接坑：内置算子的 aclnn 实现在 libopapi.so，不在 libnnopbase.so
g++ ... -lopapi -lnnopbase -lascendcl        # 否则 undefined reference to `aclnnFFNV3'
# 2) 参数约束（都是实测撞出来的）：
#    - dense 形态（无 expert tokens）**只支持 fp16**：bf16 报 "only support dtype float16 without expert tokens"
#    - GLU 形态要求 innerPrecise=1（传 0 报 "Detected glu, inner precision is not right"）
# 3) 过了参数校验后，执行阶段报 "check graph != nullptr failed" —— **原因待查**
```

> ⚠️ **自我纠错（重要）**：我一度判定"本机 SOC 没有 `FFN` 的 kernel ⇒ 不可执行"，
> **那是错的，查法错了**：内置 kernel 按**分类目录**组织，不是按算子名放在顶层。
> 按同样错查法，`swi_glu` / `matmul` 也"查不到"，但它们**都能跑**。正确查法：
>
> ```bash
> ls /usr/local/Ascend/cann-9.0.0/opp/built-in/op_impl/ai_core/tbe/kernel/ascend910_93/ops_transformer/ | grep ffn
> #   → ffn/            ← kernel 就在本机
> #   → ffn_to_attention/  ffn_worker_batching/  grouped_matmul_swiglu_quant(_v2)/ …
> ls .../kernel/ascend910_93/ops_nn/ | grep glu
> #   → swi_glu/  glu/  clipped_swiglu/  ge_glu_v2/  swi_glu_quant/ …（→ **GLU 家族里没有 SiTU**）
> ```
>
> ⇒ 修正后的结论：**华为的融合算子在本机 SOC 下都有 device kernel（跑在 NPU 上）；
> 我直调 `aclnnFFNV3` 失败的原因仍未查清**（见下面的约束矩阵）。
> **"查不到"≠"不存在"—— 这次是查法本身出问题**（和 §1.2 的"清单里没有"是同一类教训的两个面）。

**★ 约束矩阵（6 种组合全试完，这才是"失败点到底在哪"的答案）**：

| 形态 | dtype | innerPrecise | 结果 |
|---|---|---|---|
| dense（ET=nullptr） | **fp16** | 1 | ⚠️ 参数全过 → **建图失败**（`graph != nullptr`） |
| dense | bf16 | — | ❌ `x only support dtype float16 without expert tokens` |
| GLU + ET(E=1) | fp16 / bf16 | — | ❌ `Detected glu, expert tokens should be nullptr` |
| GLU + dense | fp16 | 0 | ❌ `Detected glu, inner precision is not right` |
| 非 GLU + ET(E=1) | bf16 | 1 | ❌ `FFN bfloat16 is only support high precision now` |
| 非 GLU + ET(E=1) | bf16 | **0** | ⚠️ **参数全过 → 建图失败**：`This is an error in FFN launch aicore` |

**⇒ 三条最终结论（可复现）**：

1. `aclnnFFNV3` 的**参数约束已全部摸清**（上表：GLU 必须 dense + fp16 + innerPrecise=1；
   非 GLU 才能带 expertTokens + bf16 + innerPrecise=0）；
2. **无论哪种合法组合，本机都卡在建图 / 启动 AI Core 那一步** ⇒
   **"华为 `FFN` 融合的实测收益"在本机拿不到** —— 失败点在**建图层**，不是参数、也不是 kernel 缺失；
3. ⇒ **图级对比里"华为那侧的实测"这一格，我标「未测」，不编数。**

### 1.4 ★ 为什么拿 `SwiGlu` 当对手（这个质疑要正面回答）

**先说结论**：**CANN 的 GLU 家族全是「固定激活」，没有任何一个能配出 SiTU** —— 这才是"补缺"的硬证据。

```c
// 三个 GLU 变体的 aclnn 接口（都查过本机头文件）
aclnnGluGetWorkspaceSize(self, dim, out, ...)            // 功能：GLU(a,b) = a ⊗ σ(b)   ← 固定 sigmoid，无激活参数
aclnnSwiGluGetWorkspaceSize(x, dim, out, ...)            // 固定 silu(gate)·up
aclnnGeGluGetWorkspaceSize(self, dim, approximate, ...)  // 固定 gelu（approximate 只选 tanh/none 近似）
// FFN 的 activation 枚举：fastgelu/gelu/relu/silu/geglu/swiglu/reglu  ← 也不含 SiTU
```

**为什么最终选 `SwiGlu`**：

| 候选 | 激活 | 适不适合当对手 |
|---|---|---|
| **`SwiGlu`** | `silu(gate)·up` | ✅ **最合适**：GLU 家族里最标准、最常被对标（主流 LLM 用它），且**搬运量与 SiTU 完全一致**（读 2d + 写 d）⇒ 差异能干净地归因到"激活计算量" |
| `Glu` | `a ⊗ σ(b)` | 🟡 更简单（1 个 sigmoid，up 直通），**语义离 SiTU 更远** |
| `GeGlu` | gelu | 🟡 同上 |
| `FFN` | 整层 MLP | ❌ 粒度不同（整层 vs 激活级），且本机建图失败（§1.3） |

**但它的局限必须自己先说**：`SwiGlu` 只有 **1 个超越函数**，SiTU 有 **3 个**（2×tanh + sigmoid）
⇒ **"我慢 2.19x"不能直接归咎于实现**。所以才有 `docs/14` §18 的**变体对照实验**把
**数学成本**与**实现成本**分开：把超越函数全去掉后我能跑到 **240 µs ≈ 它的 226.7 µs**（`mte2` 占用也一致）
⇒ **差距 100% 来自超越函数**，不是搬运实现差。

> **一句话**：拿 `SwiGlu` 比，不是因为它"最公平"，而是因为**它是唯一能同维度比的对象**（同类 GLU + 同搬运量）；
> 而"我慢"这件事，我**没有停在跟它比**，而是继续拆到"数学成本 vs 实现成本"。

**★ 追问「华为不是没实现 SiTU 吗？那比什么？」—— 分母和参照是两个角色，不能混**：

| 角色 | 该用什么 | 回答什么问题 | 为什么必须这样 |
|---|---|---|---|
| **分母**（算收益倍数） | **等价 torch 组合** | "**有没有必要写这个算子**" | 拿 `SwiGlu` 当分母 = 用**不同函数**算比值 = **假命题**（口径 A） |
| **参照**（看实现水平） | **同族最强内置算子**（`SwiGlu`） | "**离同族最好还差多少**" | 不跟最强比，"快 3.5x"就是**挑软柿子** |

- **"华为没有 SiTU" 只说明"位置空着"（补缺），不说明"我的实现好"** ⇒ 两件事必须分别回答。
- 只报分母会怎样：对方必追问「那跟华为的算子比呢？」⇒ **主动摆出最不利的对比，比被问出来强**。
- 比之前要声明**能比什么**：✅ 时间/带宽（同搬运量）、✅ 融合收益幅度；❌ "谁算得对"（函数不同）。

> 类比：造一个**国外没有的规格的螺丝** —— 规格上没对手（补缺），但**制造工艺仍有参照**（最接近的规格能做到什么精度）。
> **"没有同规格" ≠ "没有参照"。**

> **所以"图级能不能做收益对比"的准确答案是**：**功能与账面能比（①②），华为侧的实测收益在本机拿不到（③），
> 而我自己的融合收益已经实测且是负的（④）**。
> ⇒ 当前**不该急着比**，该做的是**先把自己的融合打平内置 `MatMul`**（根因：自写 GEMM tiling 只到峰值 4%，`docs/14` §16.6）。

## 2. 收益总账（三层 + 证据等级）

参数：`d=11008`（`intermediate_size`）、`H=4096`、`B=8`（`attn_res_block_size` → `nvec=9`）、prefill `4096` token、bf16（`../benefit_total.py` 的默认值）。

| # | 收益项 | 每 token 省 | 性质 | 证据等级 |
|---|---|---|---|---|
| ① | SiTU-GLU：torch 组合（6 个 elementwise）→ **我的 1 个 kernel** | `12d` = 132,096 元素 = **258 KiB** | 补缺 | ✅ **实测**：`docs/14` §14.3 |
| ② | SiTU-GLU：独立算子 → **融进 GEMM epilogue** | `4d` = 44,032 元素 = **88 KB**（88,064 B） | 优化 | ⚠️ **账面**（融合算子未跑通） |
| ③ | AttnRes：朴素 4 算子 → **单 kernel**（内部已融 norm+proj 折点积） | `8(B+1)H` = 294,912 元素 = **576 KiB** | 补缺+融合 | ✅ kernel 实测；融合已验证 `docs/11` §2 |
| ④ | LatentMoE 图接线 | —— | **使能**（0→1，不按带宽量化） | 设计结论 |
| ⑤ | double buffer / tiling 参数化 | **0** | 性能 | ❌ **实测无收益**：`docs/14` §9 |

**阶梯合计（不可跨行相加）**：`12d + 4d + 8(B+1)H` ≈ **471,040 元素/token ≈ 920 KiB/token**。

> 为什么 ①② 不能相加？因为它们是**阶梯**：①是「torch 组合 → 独立算子」，②是「独立算子 → 融合版」。
> 能相加的只有「最终版 vs 原始实现」（即 `12d + 4d`）。见 `../benefit_total.py` 的 `summary()`。

### 2.1 ① 的实测数字（唯一的同 shape 对比）

| shape | 我的算子 | 等价 torch 组合 | 加速比 | 有效带宽 | 达标率 |
|---|---|---|---|---|---|
| `(8,512,22016)`（450 MB 搬运） | **0.4568 ms** | 2.0319 ms | **4.45x** | 987 GB/s | 77.6% |
| `(2,7,4096)` | 0.0152 ms | 0.1170 ms | **7.68x** | —— | 1.5%（启动开销主导） |
| C++ 直调 `3584×11008` | 0.4003 ms | —— | —— | 985 GB/s | **81.5%** |

- 峰值参照：**1208.7 GB/s**（C++ `bw_test`）/ **1272.9 GB/s**（torch copy）。
- 小 shape 的「达标率低」不是 kernel 差：理论下限只有 0.0001~0.0012 ms，实测 0.015~0.022 ms 被**启动开销（15~20 μs）**主导。
  ⇒ **小 shape 的判据要换成「启动开销 + 搬运」**，详见 `docs/04`。

### 2.2 ★「收益倍数」的分层答案（被问"多少倍"时照这个答）

**同一个优化，在不同层的倍数完全不同 —— 这不是数字缩水，这就是 Amdahl + 层次结构。**

| 层 | 分母（口径） | 倍数 | 出处 |
|---|---|---|---|
| ④ **算子级**（elementwise） | **等价 torch 组合**（6 个 op） | **3.5x ~ 7.5x** | `docs/14` §14.3、§20 |
| ④ 算子 vs **同类内置算子** | 华为 `SwiGLU`（同卡同判据） | **0.46x（我慢 2.19x）** —— **如实说** | 本文 §5 |
| ③ **整层 MLP** | 官方 `KimiMLP` 同权重，vs reference `act_fn` | **1.69x** | `docs/14` §19 / L2 |
| ① **系统 TPOT** | mini 引擎，vs reference | **1.08x（+7.3%）** | `docs/14` §19 |
| ① **系统 TTFT** | 同上 | **1.00x（−0.1%）** | `docs/14` §19 |
| ③ 融合算子（GEMM+SiTU） | vs 两段式 | **0.05x（负收益）** | `docs/14` §16 |

**话术（背这段）**：

> 「问倍数先问**口径：分母是谁**。我的分母一律是「**等价 torch 朴素实现**」——
> 因为华为没有 SiTU 变体，拿它当分母是假命题。
> 然后**分层报**：算子级 **3.5~7.5x**、整层 MLP **1.69x**、系统 TPOT **1.08x**。
> 倍数逐层下降是 **Amdahl 的必然**（decode 每步要读 3 GiB 权重），不是数字注水 ——
> 反过来，**谁要是给你一个「端到端 7 倍」的数，那才该被怀疑**。」

### 2.3 ★ 真权重分布下会不会退化？（`scripts/real_weight_robustness.py`）

此前的数字都在**随机高斯**输入上取的。而 K3 的真实链路是
`MXFP4 权重 → 软件反量化 →（动态 MXFP8 激活）→ 进 SiTU-GLU`，
所以必须补上"**真实分布下收益会不会退化**"这一问。四类分布 × 三个 shape（d=11008 真实值）：

| shape | gauss（对照） | **mxfp4**（4bit 台阶） | **outlier**（通道×50） | **mxfp4+outlier** |
|---|---|---|---|---|
| `(128, 22016)` | 6.40x | 4.82x | 6.50x | 7.54x |
| `(512, 22016)` | 3.75x | 3.61x | 3.61x | 3.47x |
| `(2048, 22016)` | 3.69x | 3.63x | 3.69x | 3.64x |

- **正确性 12/12 通过**（判据 `max_rel < 1e-2`）；MXFP4 往返后 max_rel 反而更小（**7.748e-3**，量化后的值更规整）
- **加速比几乎不变**（3.47x ~ 7.54x）⇒ **收益倍数不是"随机数据上的假象"**
- outlier 不影响：`tanh`/`sigmoid` 本身会饱和，极值被压住

> 口径重申：这是**输入分布**层面的贴近（模拟反量化与 outlier），**不是**加载了真正的 K3 权重
> （1.5 TB / 96 分片，本机不具备条件）。真权重到位后，`test_situ_real.py` + 本脚本可直接复跑。

### 2.4 ★ 自证：收益倍数的「分母」跑在 NPU 上（不是 CPU）

**疑问**：`pip list` 里写的是 `torch 2.10.0+**cpu**` —— 那"等价 torch 组合"这个分母，是不是在 CPU 上跑的？
如果是，加速比就是假的（会差几百倍）。

**答案：不是。** `+cpu` 是 **PyTorch wheel 的名字**（PyTorch 官方只发 CPU/CUDA 版），
昇腾通过 **`torch_npu` 插件**（`PrivateUse1` 后端 + aclnn 接入）把 NPU 挂到 torch 上 ⇒ **计算在 NPU 上**。

| 证据 | 值 |
|---|---|
| `torch.npu.is_available()` | **True** |
| `device_count` / `get_device_name(0)` | **2** / **Ascend910_9382** |
| msprof 能采到什么 | `aiv_vec_time` / `aiv_mte2_time`（**只有 NPU kernel 才有这些字段**） |
| 本卡实测峰值带宽 | **1271.6 GB/s**（大张量 copy） |

**对照实验（同一段 torch 组合，只换 device）**：

| device | 耗时 |
|---|---|
| CPU | **35.79 ms** |
| NPU | **0.1209 ms** |
| 比值 | **295.9x** |

⇒ 若分母在 CPU，收益倍数会是**几百倍**量级；而实测是 **3.5~7.5x** ⇒ **分母确定在 NPU**。

**确实在 CPU 上跑的环节（都在"无害位置"）**：

| 环节 | 为什么无害 |
|---|---|
| reference golden（`reference/situ.py`） | 它是**标准答案**，不是被测对象；NPU 结果 `.cpu()` 后与它比对 |
| host 侧调度 / tiling / 参数准备 | 任何 NPU 程序都如此（kernel 在 device，启动与 tiling 在 host） |
| `real_weight_robustness.py` 的 MXFP4 造数 | 只用于**造输入**，造完 `.npu()`，**不参与计时** |

### 2.5 ★ 坐标系：谁的数、在哪个设备上算的（一张表说清）

实验里同时存在**四种角色**，落在**两个设备**上 —— 混了就会得出错误结论。实测（同一段脚本打印 device）：

| 角色 | 在哪算 | dtype | 用途 | 为什么在这里 |
|---|---|---|---|---|
| ① **「等价 torch 组合」**（性能分母） | **NPU** | bf16 | 收益倍数的分母 | 它就是"**没有自定义算子时，框架真实要付的成本**"（vLLM/官方实现就是这 6 个 elementwise），必须在**同一设备**上测 |
| ② **自研算子**（`aclnnSituAndMul`） | **NPU** | bf16 | 被测对象 | AscendC kernel 跑在 AI Core |
| ③ **华为内置算子**（`npu_swiglu` / `MatMulV2` / `aclnnChunkKdaFwd`） | **NPU** | bf16 | 同卡同判据对测 | 同设备、同判据才可比 |
| ④ **精度 golden**（`reference/situ.py`） | **CPU** | bf16（跟随输入） | 对拍的"标准答案" | **正交参考**：不同设备 + 不同实现路径，才**发现得了共同的错** |

```
你的代码
  ↓  torch.tanh(...) / torch.ops.kimi3_ops.situ_and_mul(...)
torch 本体（wheel 名带 +cpu，那是编译标记，不是运行位置）
  ↓  torch_npu 插件（PrivateUse1 后端）派发
aclnn C 接口（CANN 层）   ← 我的 aclnnSituAndMul、华为的 aclnnSwiGlu 都在这一层
  ↓
AscendC device kernel  →  NPU 的 AI Core（真正算的地方）
```

**三个容易搞错的说法（逐个纠正）**：

| 说法 | 对不对 | 正确说法 |
|---|---|---|
| 「我开发的是跑在 NPU 的 torch 算子」 | 🟡 一半 | **跑在 NPU 上是对的**，但它是 **CANN 算子**（AscendC kernel + aclnn），**torch 只是调用方之一**（另一条路是裸 C++ 直调 aclnn） |
| 「精度比的是 CPU 的 torch」 | ✅ **对** | golden 显式 `x.cpu()` 在 CPU 上算 —— 这是**故意的**：被测与参考若共用同一套实现，就发现不了共同的错误 |
| 「华为的是 NPU 的 torch」 | 🟡 要分 | **华为的算子**（`SwiGlu`/`FFN`…）是 **NPU 的 CANN 算子**（与我同类）；**`torch_npu`** 才是华为出的"让 PyTorch 跑昇腾"的**插件** —— 两者是不同东西 |

> **一个必须讲清的细节**：golden 的 dtype 是 **bf16（跟随输入）**，而**自研 kernel 内部是 fp32 中间计算**
> （Cast bf16→fp32 → Tanh/Sigmoid → 转回 bf16）。所以对拍结果常常是"**自研更准**"：
> torch 组合是**逐算子 bf16（约 6 次舍入）**，自研只有首尾两次转换。
> 这也是为什么判据必须写 `±(atol + rtol·|ref|)` 而非纯相对误差 —— `|ref|≈0` 处会把正常误差放大成假失败
> （实测踩过：改判据前 6 个算子全 FAIL）。

## 4. prefill vs decode（口径 B 的算例）

```
prefill：省的量 × token 数 → 4096 倍放大
decode ：每步要读整层权重 ≈ 1.38 GB（H × 2d × 2B × 8 专家）
         省的 920 KiB 只占 0.065% → 可忽略
```

⇒ **收益只对 prefill 成立**。被问「端到端提升多少」时，拿 decode 的数字去说就是错的。

**优化进展（完整实验矩阵见 `docs/14` §18）**：
✅ **已做** ① —— β=4 时把 `tanh(g/4)` 与 `σ(g)` 压成**一次 `Exp`**（`t=e^{−g/2}`）：dur 457 → **395 μs（-13.6%）**、
达标率 77.6% → **89.8%**，且对拍 PASS、`β≠4` 回退路径也验证过；
⬜ 未做 ② 多项式近似替掉 `Exp`（`Exp` 仍是最大单项，≈110 μs 级）、③ 减 Cast。
**目标不变：把 V 时间压到 ≈220 μs（= 内置 SwiGLU 的量级），让访存重新成为瓶颈。**

**⚠️ 口径陷阱（实测踩到）**：内置算子按口径 A 算出达标率 **179%** ⇒ copy 测的峰值（1:1 读写）**不能给读多写少的算子当分母**（脚本已加自检：>100% 即报警）。**对外只报同口径的时间/带宽比，不报绝对达标率。**
